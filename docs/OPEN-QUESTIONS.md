## 確定した選択

2026-09-21にQ01〜Q13を確定した。以下は採用した内容と、付いた条件。

### Q01：CSV出力の意味

案A（アプリ管理下のデモ勤務表への正式採用）。ADR-016の提案をそのまま採用する。
案Bを選ぶと成果は「変更案の出力」であり、勤務への自律反映は完了しない（RFC-012 §4）。

### Q02：必要人数の意味

各区間ちょうど1人。承諾時間を自動で短縮しない（ADR-005、撤回していない）。

**条件**：ある組合せが不成立でも、それは「その組合せ」の話であり、案件全体を終了しない。
他の合法な組合せや返信待ちの候補があるなら調整を続ける（RFC-009 §6、A11）。

**A16の期待値**：まず「重複する計画を採用しない」を期待値とする。案件を引き継ぐ条件は
別に定める（候補枯渇・期限・上限に達したとき）。

### Q03：分断された空き時間

範囲外として明示的に拒否する。`OUT_OF_SCOPE`で返す。

**条件**：中間の勤務済み時間を埋めて一つの区間へ戻さない（RFC-009 §5）。その候補を
使えなくても、他候補の調整は続ける。

### Q04：元勤務の部分欠勤

全時間欠勤のみ。**今回は追加しない。** Day 2終了後の機能追加も行わない。
部分欠勤は次段階へ回す。

### Q05：日跨ぎ

明示的に拒否する。黙って同一営業日へ丸めない。

### Q06：月次上限で数える時間

完了済みを含む予定区間で検査する。名称は「月次割当上限」であり、実労働時間の上限判定では
ない（勤怠実績を取得していない）。取消と欠勤区間は除く。completedになっただけで枠を
復活させない。

**条件**：月内入力の完全性が必須。対象月の全入力、または「他日は空」と分かる完全な
fixtureが要る。欠けた日を0と推定しない（A09）。

### Q07：業務完了と通知

正式採用・読戻し・必要通知の受付まで。**非選定通知と募集終了通知も対象に含める。**
確定した相手だけに通知して他の候補を待たせたままにしない（RFC-011 §7）。

### Q08：言語・DB・実稼働

TypeScript、Next.js App Router、PostgreSQL 18、番号付きSQL migration（pg）、Vitest。
ADR-003の候補構成を採用値へ昇格する。ADR-003は差し替えず、確定注記を追記した。

理由：Aがフロント寄りフルスタック経験者であり、RFC-012 §3.1の所有パス表をそのまま
使える。両名の別の得意スタックを優先する根拠が出ていない。

実装上の仮定（採用済みのプロダクト判断ではない。変更可能）：

| 項目 | 値 | 理由 |
|---|---|---|
| Node.js | 20.19.5 | ADR-003の初期案は「Node 24系」。実機に入っていた20系がNext.js 16の要件（>=20.9.0）を満たすため、導入作業を増やさずこれをチーム共通版とした |
| TypeScript | 5.9系 | 最新は7系だが、4日間の期間中に新しいコンパイラを持ち込む危険を避ける |
| Vitest | 4.1系 | 5系はNode 22.12以上を要求し、上記のNode 20と両立しない |

Bの実機でNode版が異なる場合は、`.nvmrc`（20.19.5）に合わせる。

### Q09：自然文承諾の対応範囲

**判定対象は返信単体ではなく、元打診＋返信＋現在の承諾＋確定前後の状態。**
文型の一覧だけで判定しない。

| 入力 | 扱い |
|---|---|
| 「大丈夫です」 | 元打診から全条件が一意なら承諾候補 |
| 「19時からなら行けます」 | 終了時刻を含む条件が一意なら承諾候補。不明なら確認へ |
| 「その時間は無理」「取り消します」 | 対象が一意なら、時刻の再記載が無くても辞退・撤回として処理する |
| 曖昧な訂正 | 確認へ回し、**旧承諾による選定も保留する** |

**「承諾として採用しない」と「返信を無視する」は別。** 承諾に使えない返信も、記録し、
辞退・撤回・保留として状態へ反映する。

fixtureは例文だけにしない。元打診、既存の承諾、確定前か確定後か、期待結果をセットにする
（RFC-011 §3・§4）。

### Q10：件数・回数・費用等の上限（暫定）

| 項目 | 値 | 位置づけ |
|---|---|---|
| 最大スタッフ数 | 8 | 旧案の初期候補を採用 |
| 時間の刻み | 15分 | 同上 |
| 最長追加勤務 | 4時間 | 同上 |
| `case_call_limit` | 24 | **検証前の上限候補。十分な回数だという保証ではない** |
| `case_spend_limit`／`run_spend_limit` | 未定 | 単価判明後に設定。未設定なら有料呼出しを開始しない |

24callの根拠：返信解釈が1人1callなら8人で8callであり、10callにはまだ達しない。
追加確認、訂正、schema修復、再試行、モデルによる次行動提案まで含めると不足し得る、
というのが正確な理由。上限到達時に安全へ引き継げることを試験する（A18）。

費用見積り（`ORCA_ESTIMATED_MICRO_USD_PER_CALL`）は、正の整数であるだけでなく、
入力長・出力上限・候補モデル単価から**保守的に**設定する（RFC-004 §7）。

### Q11〜Q13：状態の出口と引き継ぎの意味

[ADR-022](adr/ADR-022-handoff-and-outcome-retention.md)へ記録した。矢印の追加だけでなく、
`HandedOff`の意味を「自動調整を終了し、人へ対応を引き継いだ」に変更し、採用事実
（未採用・採用済み・成否不明）を案件状態と別に保持する。

案件を終端にすること自体はA13/A18の必須条件ではない。事実を保持して人へ渡せればよく、
案件を終わらせる目的で不明状態を消さない（RFC-011 §5末尾）。

## 実装上の停止条件

### Q10：件数・回数・費用等の上限（未決のまま）

2026-09-21時点でOrcaRouterのAPIキー・接続先・単価が未取得のため、**実呼出しを行って
いない**。予算予約（`src/adapters/orca/budget.ts`）と使用量記録（`usage.ts`）の枠だけを
実装し、次の条件のいずれかで呼出しを開始しない（ADR-007）。

- 接続情報、`case_spend_limit`、`run_spend_limit`、1呼出しの見積りのいずれかが未設定：
  `createModelGateway`が`UnconfiguredModelGateway`を返す。
- 1呼出しの費用見積りが0以下または整数でない：見積り0を許すと金額上限の比較が常に成立し、
  予算が無効になる。

金額は**USDの整数micro単位**で扱う（RFC-004 §7の採用済み決定）。円換算は表示時に換算日時と
レートを添えて行い、内部では円を持たない。Q10で未決なのは**上限値**であって、通貨・表現では
ない。設定名もRFC-004 §7の`case_call_limit`／`case_spend_limit`／`run_spend_limit`に合わせる。

`case_call_limit`が未設定の場合は、Q10で暫定確定した**24call／案件**を既定値として適用する
（`DEFAULT_CASE_CALL_LIMIT`）。ADR-007の10call／案件は順次打診を前提にした値のため
置き換えた。未設定であることは「上限なし」を意味しない。

予約は`request_id`で冪等にし、`request_hash`を台帳へ保存して再予約時に照合する。
同じIDで内容が異なる要求は`OPERATION_CONFLICT`で拒否する（ADR-006 / D07）。

**予約が一重でも、外部呼出しまで一重になるわけではない。** すでに予約済みの要求は、
保存済み結果を返すか、成否を照合するまで再送しない。結果が確認できない場合は
`RECONCILE_REQUIRED`として人の対応へ回す（AGENTS.md）。`request_id`は呼出し元が
永続化し、adapter側で採番しない。課金不明は`UNKNOWN_CHARGE`として予約を残す
（RFC-004 §7）。

### migrationの番号割当（実装上の運用）

RFC-012 §3.1は`src/adapters/db/migrations/`を「B作成・A承認」としている。これを維持した
うえで、`0001_worker_runtime.sql`のみworker基盤としてAが作成した。業務テーブルは0002以降を
Bが使う。所有区分の変更ではなく、番号の衝突を避けるための運用。

Q11〜Q13はRFC-011 §5の状態図に出口が無い経路で、2026-09-21の実装レビューで見つかった。
状態の**意味**の変更を伴うため、[ADR-022](adr/ADR-022-handoff-and-outcome-retention.md)へ
記録した。矢印を足すだけでは、採用済みの案件を「未確定」と表示する。

対応ADR：[016](adr/ADR-016-csv-adoption.md)、[018](adr/ADR-018-scope-open-decisions.md)。決定時は選んだ値・日付・理由を追記し、RFC・fixtureの期待値を同時に更新する。

Q07は業務完了の時点だけが未決。案件・相手別対話・勤務表更新・メッセージ配送の状態を分離する方針は[ADR-017](adr/ADR-017-state-boundaries.md)で承認済み。

## 確定した選択

2026-09-21にQ01〜Q13を確定した。以下は採用した内容と、付いた条件。

### Q01：CSV出力の意味

案A（アプリ管理下のデモ勤務表への正式採用）。ADR-016の提案をそのまま採用する。
案Bを選ぶと成果は「変更案の出力」であり、勤務への自律反映は完了しない（RFC-012 §4）。

### Q02：必要人数の意味

各区間ちょうど1人。承諾時間を自動で短縮しない（ADR-005、撤回していない）。

**条件**：ある組合せが不成立でも、それは「その組合せ」の話であり、案件全体を終了しない。
他の合法な組合せや返信待ちの候補があるなら調整を続ける（RFC-009 §6、A11）。

**A16の期待値**：まず「重複する計画を採用しない」を期待値とする。案件を引き継ぐ条件は
別に定める（候補枯渇・期限・上限に達したとき）。

### Q03：分断された空き時間

範囲外として明示的に拒否する。`OUT_OF_SCOPE`で返す。

**条件**：中間の勤務済み時間を埋めて一つの区間へ戻さない（RFC-009 §5）。その候補を
使えなくても、他候補の調整は続ける。

**実装上の明確化（2026-09-22）**：独立した複数の可能時間窓そのものは分断扱いにしない。
候補時間がいずれか1つの窓に完全に収まる場合は許可し、1つの窓が既存勤務の差し引きで
分断された場合だけ`OUT_OF_SCOPE`で拒否する。

### Q04：元勤務の部分欠勤

全時間欠勤のみ。**今回は追加しない。** Day 2終了後の機能追加も行わない。
部分欠勤は次段階へ回す。

### Q05：日跨ぎ

明示的に拒否する。黙って同一営業日へ丸めない。

### Q06：月次上限で数える時間

完了済みを含む予定区間で検査する。名称は「月次割当上限」であり、実労働時間の上限判定では
ない（勤怠実績を取得していない）。取消と欠勤区間は除く。completedになっただけで枠を
復活させない。

**条件**：月内入力の完全性が必須。対象月の全入力、または「他日は空」と分かる完全な
fixtureが要る。欠けた日を0と推定しない（A09）。

### Q09：自然文承諾の対応範囲

**判定対象は返信単体ではなく、元打診＋返信＋現在の承諾＋確定前後の状態。**
文型の一覧だけで判定しない。

| 入力 | 扱い |
|---|---|
| 「大丈夫です」 | 元打診から全条件が一意なら承諾候補 |
| 「19時からなら行けます」 | 終了時刻を含む条件が一意なら承諾候補。不明なら確認へ |
| 「その時間は無理」「取り消します」 | 対象が一意なら、時刻の再記載が無くても辞退・撤回として処理する |
| 曖昧な訂正 | 確認へ回し、**旧承諾による選定も保留する** |

**「承諾として採用しない」と「返信を無視する」は別。** 承諾に使えない返信も、記録し、
辞退・撤回・保留として状態へ反映する。

fixtureは例文だけにしない。元打診、既存の承諾、確定前か確定後か、期待結果をセットにする
（RFC-011 §3・§4）。

### Q10：件数・回数・費用等の上限（暫定）

| 項目 | 値 | 位置づけ |
|---|---|---|
| 最大スタッフ数 | 8 | 旧案の初期候補を採用 |
| 時間の刻み | 15分 | 同上 |
| 最長追加勤務 | 4時間 | 同上 |
| `case_call_limit` | 24 | **検証前の上限候補。十分な回数だという保証ではない** |
| `case_spend_limit`／`run_spend_limit` | 500000／5000000 microUSD | 2026-09-22に設定（下記） |
| 呼び出すモデル | `orcarouter/free` | 2026-09-22に設定（下記）。有料モデルへ振らない |

24callの根拠：返信解釈が1人1callなら8人で8callであり、10callにはまだ達しない。
追加確認、訂正、schema修復、再試行、モデルによる次行動提案まで含めると不足し得る、
というのが正確な理由。上限到達時に安全へ引き継げることを試験する（A18）。

費用は**1呼出しごとに見積もる**。固定額を予約しない（RFC-004 §7）。長い返信や高い
モデルへ振られた場合に実費が予約を超え、並行呼出しが上限を通り抜けるため。次を
決定的に固定する。

| 項目 | 設定 | 既定 |
|---|---|---|
| 入力長の上限 | `ORCA_MAX_REPLY_CHARS` | 1000文字。超える返信は呼出さずに拒否 |
| 出力トークン上限 | `ORCA_MAX_OUTPUT_TOKENS` | 512。要求にも `max_tokens` として含める |
| 入力単価（最大） | `ORCA_INPUT_MICRO_USD_PER_KTOK` | 未設定。候補モデルのうち最も高いもの |
| 出力単価（最大） | `ORCA_OUTPUT_MICRO_USD_PER_KTOK` | 未設定。同上 |

見積りは切り上げる。トークン数の上限は**UTF-8のbyte長**から計算し、1 byte = 1トークンを
上限とする（`estimateInputTokens`）。Routerが候補モデルを選ぶ構成ではtokenizerを特定
できず、byte fallbackを使うtokenizerでは1文字がUTF-8の3〜4 byteへ分割されるため、
文字数を基準にすると上限にならない。単価が未設定なら有料呼出しを開始しない。

#### 2026-09-22：接続先とモデルを設定した（金額の位置づけが変わった）

OrcaRouterのワークスペースを確認して次を設定した。

| 項目 | 値 |
|---|---|
| OpenAI互換のbase URL | `https://api.orcarouter.ai/v1` |
| モデル | `orcarouter/free`（無料モデルへ振るRouter。ウォレットに触れない） |
| 入力／出力単価 | 各 1 microUSD/Ktok |

**重要：金額の上限は、この構成では実質的な歯止めになっていない。**
無料モデルの実費は $0 で、単価は名目値である。schema が 0 を受けないのは「未設定」と
「0」を区別するためで（ADR-007）、正の最小値を置いて予約が実費を下回らない向きへ
倒している。結果として `case_spend_limit`／`run_spend_limit` には到達しない。

実際に効く歯止めは **`case_call_limit`（回数）**だけである。金額上限があるから安全、と
読まないこと。最初の実呼出しでは `ORCA_CASE_CALL_LIMIT=1` まで絞る。

ワークスペースのウォレット残高は $0.00、支払い方法も未登録なので、仮に有料モデルへ
振られても課金されずに失敗する。**有料モデル（`orcarouter/auto` 等）へ切り替えるなら、
単価と金額上限をこの表ごと決め直すこと。** 現在の値は無料モデル前提の名目値で、
有料構成の上限としては使えない。

#### 2026-09-22：出力上限が効いていない（見積りの前提が崩れている）

初回の実呼出しで観測した。要求に `max_tokens: 512` を入れているのに、実測の
`completion_tokens` は **1085** だった。原因は振り先が推論モデルであることで、
`completion_tokens_details.reasoning_tokens` に推論分が入り、`max_tokens` はこれを
縛らない（`max_completion_tokens` へ替えても同じ挙動だった）。

RFC-004 §7 は「入力長・**出力上限**・単価から保守的に予約する」としている。出力上限が
守られないなら、**予約額は実費を下回り得る**。この回は入力側の見積り（UTF-8 byte長を
1トークンとする上限）が十分に大きく、予約6 microUSD に対し精算4 microUSD で収まったが、
それは偶然の余裕であって保証ではない。

当面の扱い：

- 実測が要求上限を超えたことを `UsageRecord.outputLimitExceeded` に記録し、画面へ出す。
  件数が0でなければ前提が崩れている、と読めるようにした。
- 推論トークンは `reasoningTokens` として**分けて**持つ。出力トークンへ畳むと、
  上限が守られなかったことに気付けない。
- 無料モデル構成では実費 $0 なので実害はない。**有料モデルへ切り替える前に、
  出力側の見積りをどう保守化するかを決めること。** 1件の観測（512 に対し 1085）から
  係数を決めるのは一般化しすぎなので、ここでは決めない。

## 実装上の停止条件

### Q10：呼出しを開始しない条件（2026-09-22に接続先を設定）

2026-09-21時点ではOrcaRouterのAPIキー・接続先・単価が未取得で、**実呼出しを行って
いなかった**。2026-09-22に接続先・モデル・上限を設定した（上記「接続先とモデルを
設定した」を参照）。呼出しを開始しない条件そのものは変えていない（ADR-007）。

- 接続情報（`ORCA_BASE_URL` / `ORCA_API_KEY` / **`ORCA_MODEL`**）、`case_spend_limit`、
  `run_spend_limit`、候補モデルの単価（`ORCA_INPUT_MICRO_USD_PER_KTOK` /
  `ORCA_OUTPUT_MICRO_USD_PER_KTOK`）のいずれかが未設定：`createModelGateway`が
  `UnconfiguredModelGateway`を返す。単価が無ければ保守的な見積りを作れず、予約が
  実費を下回り得る。モデルIDに既定値を置かないのも同じ理由で、どれを呼ぶか決まって
  いなければその単価も決まっていない。
- 算出した見積りが0以下または整数でない：見積り0を許すと金額上限の比較が常に成立し、
  予算が無効になる。
- 返信本文が入力長の上限を超える：見積りを超える費用になり得るため、予約前に拒否する。

金額は**USDの整数micro単位**で扱う（RFC-004 §7の採用済み決定）。円換算は表示時に換算日時と
レートを添えて行い、内部では円を持たない。Q10で未決なのは**上限値**であって、通貨・表現では
ない。設定名もRFC-004 §7の`case_call_limit`／`case_spend_limit`／`run_spend_limit`に合わせる。

`case_call_limit`が未設定の場合は、Q10で暫定確定した**24call／案件**を既定値として適用する
（`DEFAULT_CASE_CALL_LIMIT`）。ADR-007の10call／案件は順次打診を前提にした値のため
置き換えた。未設定であることは「上限なし」を意味しない。

予約は`request_id`で冪等にし、`request_hash`を台帳へ保存して再予約時に照合する。
同じIDで内容が異なる要求は`OPERATION_CONFLICT`で拒否する（ADR-006 / D07）。

**予約が一重でも、外部呼出しまで一重になるわけではない。** すでに予約済みの要求は、
保存済み結果を返すか、成否を照合するまで再送しない。結果が確認できない場合は
`RECONCILE_REQUIRED`として人の対応へ回す（AGENTS.md）。`request_id`は呼出し元が
永続化し、adapter側で採番しない。課金不明は`UNKNOWN_CHARGE`として予約を残す
（RFC-004 §7）。

`EligibilityChecker.recheck` は正式採用の直前にもう一度通す（D08）。しかし
`EligibilityRecheckInput` が持つのは `SelectionInputs`——すなわち `monthlyCompleteness` と
`missingDates` だけで、**月内の実際の割当も本人の可能時間も持たない**。

PR #9 で入った `evaluateCandidateEligibility`（`src/domain/interval/index.ts`）は
`MonthlyScheduleSnapshot`（月内の割当とスタッフ条件）を要求する。いまの契約のままでは
繋げないため、`createUnimplementedEligibilityRecheck` を残している。

検討する選択：

1. `EligibilityRecheckInput` へ `MonthlyScheduleSnapshot` を足す（`recheck` は同期のまま）
2. `recheck` を非同期にし、実装側が必要な入力を取りに行く
3. `recheck` を廃し、application 側が `evaluateCandidateEligibility` を直接呼ぶ

**1を初期推奨とする。** `recheck` を同期のまま保てば、外部待ちを取引の中へ持ち込まない
（RFC-010 §5）。2は口の中でDBやGatewayを引くことになり、取引境界の規則が効かなくなる。
3は「検査した前提」をapplication側に散らし、D08の再検査が一箇所で説明できなくなる。

どの案でも、`ScheduleGateway` が月内入力を返せるようになるまで本番経路では成立しない。
契約だけ先に変えても `NOT_IMPLEMENTED` が `ScheduleGateway` 側へ移るだけなので、**Bの
CSV Gatewayと同じ変更で入れる**のが望ましい。

受入への影響：A09（月内入力不足）とA16・A17の期待値。いずれも未実行のまま。

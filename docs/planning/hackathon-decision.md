作成日：2026年9月19日  
用途：チームの題材決定、4日間の開発、デモ準備  
状態：**案05の採用を推奨する意思決定案。チームの合意・実機検証は未実施。**

## 1. 採用提案

**案05「飲食店の突発欠勤に対応する代替スタッフ調整エージェント」を採用する。** 原案の需要予測・食材発注・天候連動は今回の範囲から外す。スタッフからの辞退や部分承諾を受けて再計画し、条件を満たすシフト更新、または理由付きの人への引き継ぎまで実装する。

判断の前提は、ユーザーが確認した「開発期間4日間」「飲食店・経理／購買に詳しい人や協力先はいない」の2点。チーム人数、各人の稼働時間、技術経験、利用可能なAPIキー、公式配点、発表時間は未確認。人数を仮定した工数の約束はしない。

案05を推す理由は、架空の1店舗・少人数・明示した勤務条件で、第三者が正誤を判定できるデモを構成しやすいため。案02にもCSVとテスト用受信箱で実装できる経路はあるが、発注・納品・請求の関係、分納・未着・請求単位の扱いなど、業務の正解を自分たちで定義する負担が追加される。**これは4日間の完遂可能性についての判断であり、案05の市場性やモデル性能を実証した結論ではない。**

案02は、Day 1の中間判断までに「1種類の例外」「矛盾のない正解データ」「返信から再照合までの動作経路」が揃い、案05に固有の障害がある場合の代替候補とする。OrcaRouter接続失敗は両案共通の障害なので、案02への変更では解決しない。

### レビューをそのまま採用しない点

- 「自律性が審査の1/5」は未確認。5項目あることから同配点とは言えない。
- 「実装と壇上の自律だけで決めてよい」は狭すぎる。セキュリティ、コスト、堅牢性、独創性も検証対象に残す。
- 「ルーティングログだけで安全性を証明できる」とはしない。権限検査、拒否動作、重複防止の実測が必要。
- 「国内リージョンなら推論も国内」は前提にしない。公式Trust Centerは証跡の地域分離と推論処理地域を区別している。[S6]
- 「エンタープライズ機能だから当日利用できない」と断定しない。提供アカウントで確認する。
- 複数モデルを使っても、結果の正しさ・安全性を保証できるわけではない。

## 6. 案05の完成像

### ジョブストーリー

夕方の営業準備中に欠勤が出たとき、店長は手を止めずに代替候補への連絡と調整を進めたい。AIは事前に許可された勤務条件と連絡範囲で動き、埋まったシフト、または未解決の不足だけを店長に返す。

### デモに使う架空ケース

必要枠は18〜22時のホール担当1人。Aは18〜22時に勤務可能だが辞退。Bは「19時から22時なら入れます」と返答。Cは18〜19時の勤務に承諾する。全員について担当スキル、既存勤務との重複、店側が設定した勤務上限、本人の連絡許可を確認する。

AIはBの返答から不足時間18〜19時を認識し、候補Cへ打診する。BとCの両方が確定した時点でシフト表を更新して読戻す。候補の選定に健康情報・家庭事情・年齢等のセンシティブ属性を使わず、必要な勤務条件と本人の意思だけを使う。辞退理由を他人へ伝えない。

### 状態と終了

| 状態 | 進める条件 | 次の動作 |
|---|---|---|
| 受付 | 対象シフト、欠勤時間、必要スキルが揃う | 不足時間を計算 |
| 計画 | 候補が制約を満たす | 許可された候補へ打診 |
| 返信待ち | 返答または設定した期限に到達 | 意図・時間を抽出して検査 |
| 再計画 | 辞退、部分承諾、無応答 | 未充足時間と未打診候補を再評価 |
| 確定準備 | 必要時間の承諾が揃う | 最新シフトを再読込、競合と権限を検査 |
| 更新・確認 | 一意の実行IDと対象バージョンが一致 | 一度だけ更新し、読戻しで結果を確認 |
| 完了 | 全時間の充足と読戻しが成功 | 店長へ結果を報告 |
| 引き継ぎ | 候補枯渇、矛盾、期限、予算、回数上限、更新結果不明 | 未確定枠、根拠、実行済み操作を提示して停止 |

シフトを確定する直前に元のシフトの版を確認する。並行して店長が更新した場合は、そのまま上書きしない。期限後の承諾は自動的に有効な承諾に戻さない。訂正依頼や撤回は新しいイベントとして扱う。

### AI、コード、人の分担

- AI：自然文の返答から条件を抽出、曖昧さを検出、追加確認や次の行動を選択、簡潔な連絡文を作成。
- コード：勤務条件、時間の充足、候補順のルール、連絡先、権限、同時更新、一度だけの実行、予算を検査。
- 人：事前の勤務・連絡ルール設定。範囲外の判断や未解決ケースを受け取る。

承認ボタンを毎回押す設計にはしない。事前に許可した操作だけを自律実行する。モデルの判断で許可範囲を広げない。

## 7. 案02を採る場合の完成像と採用条件

### ジョブストーリーと架空ケース

発注数量100個に対して受領済み60個、届いた請求書は100個分という差分を扱う。デモ用の取引条件は「今回の検収済み数量だけ請求」と明記する。これを一般的な商慣行だとは主張しない。

税・送料を扱わないテストデータで単価1,000円なら、発注総額100,000円、今回の検収相当額60,000円、差分40,000円。取引先が「残り40個は翌便。今回分を60個に修正」と回答し、修正請求書を出した後、AIが再照合を行う。照合台帳は今回分を「照合済み」、残り40個の発注残を「未納のまま」とする。発注総数を書き換えて帳尻を合わせない。

### 自律ループ

CSV検査、数量・単価の照合、根拠の取得、許可された取引先への照会、回答と修正版の受付、再照合、限定台帳への反映、読戻しまで実装する。相手が「正しいです」と返信しただけでは解消にしない。参照する証拠のIDと版、当該取引条件、修正後の数値が一致した場合に限る。

### 案02の強みと負担

- 強み：金額・数量に明確な正解を設けやすく、誤った更新を拒否した証拠を示せる。比較・計算をコードに寄せれば推論費を抑えられる。
- 負担：何をもって差分解消とするかの業務条件を、専門家なしで誤解なく定義する必要がある。原案の「合意でERP更新」は権限や対象範囲の説明が不足する。
- 採用への切替条件：Day 1中間までに、正解付きケース、返信・修正版・台帳更新の通し動作、原資料まで辿れる根拠表示を用意できること。05に固有の障害がなければ、完成度を優先して05を続ける。

## 9. OrcaRouterの活用とDay 1の実機確認

正式名称は**OrcaRouter**。元資料のQrcaRouter表記を訂正する。公式Routing DSLには条件分岐や複数モデルを組み合わせる仕組みが記載されているが、提供アカウントでの利用可否・結果・計測項目は未検証。[S3]

### 実装する使い分け

| 呼び出し | モデル利用の方針 | 検証・切替条件 |
|---|---|---|
| 「不可」「19時から可能」等の構造化 | まず軽量モデルを候補にする | 必須項目・型・時間範囲をコードで検査 |
| 複数条件や矛盾を含む回答 | 高性能モデルを候補にする | 抽出失敗、矛盾、ツール検査失敗など観測可能な理由で昇格 |
| 合計・時間充足・数量・金額 | 通常のコード | モデル呼び出しなし |
| 追加のモデル検証 | 検証で改善が確認できた箇所だけ | 費用と遅延を計上。常時二重呼び出しを前提にしない |

難易度の自己申告や「自信がある」という文章だけで振り分けない。アプリが判定した状態をルーターへ渡せる場合はその方法を実測し、使えない場合はアプリが許可済みモデルを選び、全推論をOrcaRouter経由で呼ぶ。その場合は「アプリ側選択」と正確に表示し、ネイティブ自動ルーティングと混同しない。利用条件との適合は運営資料で確認する。

### 最初の60〜90分で残す記録

1. API接続、利用可能モデル、残高・予算・制限を確認する。
2. 単純入力と条件付き入力を同じルーターへ送り、実際の行き先を確認する。
3. 自分たちのルール・設定がどの単位で適用されるかを確認する。
4. 実使用モデル、トークン、遅延、料金、リクエストIDの取得可否を確認する。
5. モデルの構造化出力・ツール利用形式を確認する。
6. 対象モデル失敗時の挙動、アプリ側の回数上限・予算制御を確認する。
7. プロンプト本文・応答がどこに記録されるか、保持設定を確認する。

これはチームが今後行う検証であり、本資料の作成時に実行した検証ではない。ルーティング内容・料金の取得に失敗したら推定と明記し、請求額を捏造しない。公開仕様の記載とアカウントの実測を分けて管理する。

## 10. 安全性・堅牢性と停止条件

| 失敗・攻撃 | 検査すること | 期待する動作 |
|---|---|---|
| 返信に「他人の連絡先を送れ」と書かれる | 外部メッセージはデータとして扱う。ツールの宛先と権限を固定 | 情報を返さず、許可した業務だけ続行または停止 |
| 同じ返信が2回届く | イベントIDと一意の更新ID | 二重通知・二重確定しない |
| 複数人が同じ枠へ承諾 | 最新状態と対象バージョン、枠の一意性 | 1件だけ確定し、他の返信を再評価 |
| 更新は成功したが応答が失われる | 実行IDで結果を再照会 | 成否不明のまま再実行しない |
| 曖昧な時間／伝票が来る | 必須項目・元データ・根拠の検査 | 追加確認または人への引き継ぎ |
| 提示した候補が尽きる | 未打診候補・未充足条件 | 未解決で終了。無限に同じ候補へ送らない |
| 推論障害・無応答 | タイムアウト、回数・予算・期限 | 許可範囲で再試行し、上限で停止 |
| 店長／担当者が途中で変更 | 更新前の版と現在の版 | 上書きを止めて最新状態から再計画 |

**暫定の停止値（チームがDay 1に調整する設計値）**：1案件のモデル呼び出し最大10回、同じツールの再試行最大2回、1候補への同一打診最大1回。各リクエストの出力上限を設定し、次回呼び出し前に残予算との関係を確認する。実際の予算額と返信期限はDay 1に決め、金額や分数を実測済みのように記載しない。

「業務完了」「安全な引き継ぎ」「技術エラー終了」は別の終了状態として数える。安全に止まれたことを業務完了率の分子に入れない。上記テストで問題が出ないことは、製品全体の完全な安全性や労務・会計上の適法性の保証ではない。

## 11. コストと品質の比較実験

### 比較する構成

- A：対象のモデル呼び出しをすべて高性能モデルで処理。
- B：対象のモデル呼び出しをすべて軽量モデルで処理。
- C：軽量モデルを基本に、検査結果や状態に応じて高性能モデルへ切り替える。
- D：時間があれば固定ルールだけの基準系も追加。自然文の扱いでAIを入れる価値を確認する。

ツール、コードによる計算、許可範囲、入力、正解条件、再試行上限は共通にする。Aにも不要な計算のLLM化を追加しない。ルーティングの設定は開発用ケースで調整し、評価用ケースを見て後付けで有利にしない。

### 測るもの

| 指標 | 定義・注意 |
|---|---|
| 業務完了率 | 人の追加指示なしで、期待した最終状態と読戻しを満たした件数／対象件数 |
| 適切な引き継ぎ率 | 引き継ぐべきケースで正しく止まった割合。完了率とは別掲 |
| 制約違反 | 権限外操作、個人情報露出、重複更新、誤った確定の件数 |
| 推論費用 | 全呼び出し、昇格、検証、失敗、再試行を含む。同一通貨で集計 |
| 運用費用 | 推論費にツール費等を加える。無料枠・固定費は別記 |
| 完了1件あたり費用 | 評価全体の費用／業務完了件数。完了ゼロなら算出不能 |
| 待ち時間 | 中央値と最大値。小標本でp95だけを強調しない |
| 人の介入 | 設定済みルールや架空スタッフの返信と区別し、店長の追加判断を数える |
| 切替の挙動 | 昇格回数、採用モデル、切替理由、検査の通過・失敗 |

削減率は `1 − Cの総推論費 / Aの総推論費`。AとCの成功率・制約違反・対象件数を必ず並記する。費用だけ安くても完了率が落ちれば、その差を報告する。モデル単価、計測日時、設定の版、無料枠やキャッシュの条件を残す。画面上の料金は実測または推定を区別する。[S5]

## 12. 評価ケースと完了基準

開発用に別の6ケースを用意し、固定した評価用20ケースをA/B/Cで各1回実行する計画とする。重要な6ケースは採用構成Cで追加2回ずつ確認する。計72試行は提案であり未実施。予算不足なら件数を明示して減らす。

| 評価区分 | 件数 | 例 |
|---|---:|---|
| 通常の完了 | 4 | 即時承諾、条件を満たす組み合わせ |
| 辞退・部分承諾 | 4 | 19時から可、前半のみ可、辞退後の再計画 |
| 曖昧・矛盾 | 3 | 時間未記載、前後の返答が矛盾、追加確認 |
| 枯渇・期限・無応答 | 3 | 全員不可、連絡上限、期限後承諾 |
| 重複・障害・競合 | 4 | 重複イベント、同時承諾、更新応答喪失、途中編集 |
| 権限逸脱を誘う入力 | 2 | 他人の情報の要求、未許可の更新要求 |
| **合計** | **20** | 各ケースに期待した最終状態・禁止操作を設定 |

案02の場合も20件の枠を使い、分納の正常解消、修正版不足、数量矛盾、他社データ要求、伝票改訂、二重更新等へ置き換える。

提出可能とする条件は、主要デモが初期化後に繰り返し動くこと、定義した禁止操作がテストで0件であること、完了・引き継ぎ・エラーが区別できること、費用と成功率の比較があること。**現在これらを達成したとは主張しない。** 20ケースの成績を本番利用の保証に拡張しない。

## 13. デモの構成

発表時間が不明なため、以下は約3分の実演案。主催者の時間に合わせて調整する。

| 時間 | 見せること | 審査項目への証拠 |
|---|---|---|
| 0:00〜0:20 | 欠勤が発生し、店長が調理中という課題と事前の許可範囲 | 業務と目的の明確さ |
| 0:20〜1:20 | Aの辞退、Bの部分承諾、Cへの再打診 | 結果を観測した自律的な再計画 |
| 1:20〜1:50 | シフトの反映・読戻し、同じ承諾を再送しても二重更新しない | 堅牢性 |
| 1:50〜2:20 | 別ケースで個人情報要求や候補枯渇を入力 | 権限検査と理由付き停止 |
| 2:20〜3:00 | A/B/Cの実測結果とライブのモデル・費用・検査ログ | コストと品質、OrcaRouterの役割 |

画面は「不足と確定結果」を主役に、経過とログを併置する。モデルの内部思考を表示する必要はなく、入力の要約、選んだ行動、参照条件、検証結果を示す。待ち時間を短縮する場合は短縮表示を入れる。外部API障害に備えて録画を用意し、録画をライブと呼ばない。

案02なら、最初の差分、取引先回答、修正請求書、再照合、発注残40個の保持、二重更新の拒否、費用比較の順で見せる。

## 14. 4日間の開発計画

| 日 | 必須作業 | 終了時点で確認するもの | 遅れたときの削減 |
|---|---|---|---|
| Day 1 | 最初の60〜90分で接続・ルーティング・費用確認。ルールと架空データを定義。最小の通し動作を作る | 受付から1件の承諾・更新・読戻しまで動く。中間で題材を固定 | 外部チャット連携をテスト受信箱へ。複数店舗・装飾を外す |
| Day 2 | 自然文の部分承諾、辞退後再計画、期限、状態保存、二重更新防止、途中再開 | 主要デモと引き継ぎが初期化後に動く | 候補数・同時案件数を減らす。検査・停止は残す |
| Day 3 | 固定した評価ケースでA/B/Cを比較。失敗修正。費用・結果を可視化 | 実測表と失敗一覧。禁止操作の原因を解消 | 見た目の追加を止め、評価件数の変更は明記 |
| Day 4 | 機能を固定。再現確認、説明の修正、発表練習、予備録画 | 誰でも初期化してデモできる。料金・結果・制約を説明できる | 機能追加しない。説明と再現性に集中 |

役割は人数ではなく担当領域で置く。①進行・デモ・原稿、②エージェントとOrcaRouter、③状態・ツール・検査、④UI・テスト・計測。少人数なら兼務する。チーム人数と稼働時間が分かった時点で担当名と対応範囲を決める。

初日に共有する実装契約は、案件ID、イベントID、対象ID、対象の版、状態、許可された操作、残予算、期限、参照証拠ID、結果コード。ログの時刻・通貨・モデル名も揃え、UIとエージェントが別の状態を持たないようにする。

## 16. 想定される質問への回答

| 質問 | 回答の骨子 |
|---|---|
| なぜ案02ではないのか | 数値検証の強みはある。今回は業務専門家なしの4日間なので、明示した勤務条件で再計画を検証できる05を優先 |
| 単なる自動送信ではないか | 辞退・部分承諾・失敗から未充足条件を再計算し、次の行動を選ぶ。固定返信だけのデモにはしない |
| 固定ルールだけで十分ではないか | 制約・計算には固定ルールを使う。AIの価値は自然文の条件理解と追加確認・行動選択。評価で価値が出なければ利用範囲を減らす |
| OrcaRouterで何が良くなったか | 同一ケースの高性能固定構成と比較し、品質、費用、時間、切替理由を実測して答える |
| 人への引き継ぎは自律性が低いのでは | 事前に許可した範囲では完了まで実行。範囲外は理由付きで停止。引き継ぎを完了として数えない |
| モックでは実用性が分からないのでは | 外部接続の模擬と、実装した意思決定・状態更新を明示する。本番導入や需要の検証は未実施 |
| 実際の現場で有効か | まだ仮説。欠勤頻度、店長の対応時間、連絡許可、既存ツールとの関係を現場で検証する必要がある |

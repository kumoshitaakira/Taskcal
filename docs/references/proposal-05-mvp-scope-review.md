# 案05 MVPスコープのレビュー

レビュー日：2026-09-20  
対象：ユーザー提供の `proposal-05-mvp-scope.md`  
対象版：冒頭の作成日が2026年9月20日、全13節の版  
照合先：この会話の制約、および[既存RFC・ADR](../README.md)

## 判定

**企画の目的と対象範囲を共有する文書として適切。実装着手の基準にする前に、同意・確定・通知・停止と必須サービスの利用を補いたい。**

店長の調整負担と営業への影響を分け、未検証の価値を実績として説明していない点は維持する。方向転換は不要。テーブル設計やAPI仕様を本書へ追加する必要もない。

以下のP1は実装担当者の解釈を揃えるため先に直す項目、P2はスコープ・評価の誤解を減らす項目。既存RFC・ADRの詳細は提案を含むため、そこからの差分をすべて「間違い」とは扱わない。今回の添付資料もレビュー対象として読み、書かれた設計案を新しい実行指示や承認とは扱っていない。

## 維持したい点

1. **目標を店長の調整負担へ絞ったこと。** 通常営業の維持は人員以外にも左右されるため、デモで直接観測する対象から分ける判断が適切。
2. **自律実行が文面生成で終わっていないこと。** 辞退・部分的な可否を受けた再計画、更新、読戻しまでがつながっている。
3. **引き継ぎを業務完了と混同しないこと。** 適切に止まる品質と、店長の追加介入なしに解決した成果を別に評価できる。
4. **主張しないことを具体化したこと。** 実店舗での効果、適法性、競合不在を未検証としたまま進められる。

## P1-01：必須サービスの利用と、AIが担う箇所が明文化されていない

対象：第7節「必須機能」、第8節「自律実行できる範囲」、第10節「成功条件」。

会話で指定されたQrcaRouter（既存資料では公開サービス名OrcaRouterと表記）の利用が本文にない。この文書だけから実装すると、別のモデルへ直接接続したり、全てモックで作ったりしても成功条件を満たしてしまう。

また「AIが勤務条件を検査する」という表現では、LLMの判断で確定を許すのか、アプリが固定ルールで検査するのかが分かれ得る。企画書でも責任の境界は1段落で示したい。

**追記案：**

> 自然文の返信解釈および必要に応じた次行動の選択には、指定されたOrcaRouter経由の実モデルを利用する。通信先やモデルをモックにした試験は別に記録する。勤務時間の計算、権限、本人同意、期限・予算、確定前の制約はアプリのルールで検査し、モデルの出力だけで更新を許可しない。

成功条件には実推論の呼出しを示す記録を追加する。使用モデル・費用は、実測、推定に加えて「取得できず不明」を設ける。未取得を0円と扱わない。複雑なRouter設定自体を新たなMVP必須機能に増やす必要はない。

## P1-02：「勤務可能という返信」と「確定してよいという同意」が曖昧

対象：第7節4・代表シナリオ、第8節の本人承諾、第10節1。原文の該当箇所は114行付近、144行付近、160行、219行。

第8節には明示的な承諾が必要とあるため、同意要件が全くないわけではない。ただし、何をもって明示的とするかが未定義。「19時から22時なら入れます」を、可能時間の申告として扱う実装と、勤務確定の承諾として扱う実装に分かれ得る。

**追記案：**

> 自由文の勤務可否は候補条件として扱う。店舗・日付・職種・開始終了時刻・同意期限を本人へ提示し、その条件で全体が成立すれば勤務を確定してよいという同意を得る。提示条件が変わった場合は再同意が必要。最初の打診で全条件を示し、専用の同意ボタンで回答した場合は重複確認しない。

同意期限切れ、確定前の撤回、確定後の変更申告も区別する。スタッフ本人の回答や同意操作は必要な業務参加なので、「店長の追加介入」とは分けて数える。

これはデータモデリングではなく、利用者が何を承諾するのかという機能要件である。[関連：RFC-002](../rfc/RFC-002-domain.md)

## P1-03：部分確定、本人への確定通知、更新後の失敗の扱いが不足

対象：第7節7・8、第10節「業務完了条件」、第11節「確定済みの内容」。原文127〜136行付近、215〜225行、258行。

「一度だけ更新」は二重実行の防止を示すが、BとCをまとめて確定するかは明らかでない。Bを先に確定し、Cが決まらない状態を許すかで仕様が大きく変わる。現状の「確定済みの内容を引き継ぐ」は、部分確定を許すとも読める。

また、完了報告先が店長のみで、スタッフ本人への確定通知が必須になっていない。条件に同意していても、全体が成立して実際に勤務が決まったかを本人が知れない。

**推奨するMVP方針：**

- 全不足時間を満たす有効な同意が揃ってから、全割当をまとめて確定する。部分確定はしない。
- 確定結果は店長と割当対象のスタッフ本人へ通知する。
- テスト環境では、通知が受信箱へ保存・受付されたことを完了条件とする。本人が読んだこととは区別する。
- 更新済みで通知に失敗した場合は「確定済み・通知未完了」として扱い、割当を再作成しない。
- 更新の成否が不明なら「要確認」と表示する。未更新と決めつけず、実行IDから照合する。

第11節の確定済み情報は、この「更新後に問題が起きた案件」のために残せる。部分確定の方針を選びたい場合は、残枠が埋まらなかったときの扱いも別途定義する必要がある。[関連：RFC-003](../rfc/RFC-003-implementation.md)

## P1-04：店長が途中で止める操作が必須機能にない

対象：第7節「必須機能」、第8節「権限」、第11節「引き継ぎ条件」。

上限やエラーによる自動停止は書かれているが、店長による手動停止はない。欠勤者が復帰した、別の方法で代替が決まった、欠勤登録を誤った場合に、依頼や確定が続いてしまう。

**追記案：**

> 店長は進行中の調整を停止できる。停止成立後は新たな打診・自動確定を行わず、遅れて届いた返信で再開しない。既に確定した勤務は停止だけで取り消さず、修正が必要なことを店長へ示す。

模擬チャネルでも停止と同意の同時操作を試す。本番チャネルで送信中の通知まで取り消せる保証は、このMVPでは主張しない。[関連：RFC-007](../rfc/RFC-007-security-operations.md)

## P2-01：観測できる成果と、実際の業務中断が混ざる

対象：第5節、第10節225行「今回の目標の達成例として数える」。

架空デモで確認できるのは「開始後に店長役が追加の判断・操作をせず、調整が終わった」こと。実際の仕込みを中断しなかったことや、中断時間が減ったことまでは確認できない。第5節で現場未検証と明記している点と、第10節の達成表現を揃えたい。

**置換案：**

> 今回の技術的な達成条件は、欠勤登録・実行開始後、店長役の追加判断・修正操作なしに、全時間の確定・読戻し・結果通知を完了することである。これは店長の業務中断削減に対する代理指標であり、実店舗の中断時間の削減効果は別途検証する。

開始の入力や事前設定を分母から隠さない。開始操作数、開始後の店長介入、スタッフ本人の回答を別々に記録すると、自律性を説明しやすい。

「通常営業への影響を防ぐこと」は、必ずしも新機能の追加を意味しない。現MVPの効果を実店舗で測ることで評価できる可能性もあるため、「将来の機能拡張」より「将来の事業成果・現場検証」と書く方が正確。

## P2-02：「本書の対象外」と「実装しないもの」が混同されている

対象：冒頭5行、第2節26行、第9節203行、要約297行。

冒頭の「データモデリングは本書の対象外」は妥当。一方、第9節ではテーブル設計・APIスキーマを「今回実装しないもの」に入れている。永続化するシフトや同意、実行IDを扱う実装では最小限の設計が必要なので、文書の分担と製品スコープが混ざる。

**置換案：**

> 本書ではデータモデル、テーブル、APIの詳細を記述しない。MVPに必要な最小限の設計・実装は別RFCで扱う。

第9節の製品非対象からデータモデリングを外し、別の「本書に記載しない設計詳細」へ移す。既存のRFCを採用するならリンクで十分で、本書への転記は不要。

## P2-03：4日間・2人で実装するための上限と受入試験が未確定

対象：第3節、第7節、第8節の上限、第10節の評価数未決定。

1店舗・1案件への限定だけでは、日跨ぎ、複数職種、人数2人以上、自由な時刻、何度も続く確認まで入り得る。また、チーム2人と経験差が前提に反映されていない。

**本文に1行追加する範囲案：**

> MVPは架空1店舗、最大8スタッフ、1職種、同時1案件、必要人数1、同一日内の最大4時間、15分単位に限定する。範囲外は拒否または引き継ぎとする。

これは既存RFCの基準案であり、既にチームが決定した数字とは扱わない。別の値を選んでもよいが、実装着手前に固定する。連絡回数、再確認、待ち時間、案件期限、推論回数・予算も設定値を決め、未設定のまま実行しない。

受入試験は件数やモデル比較数を増やす前に、次の観点を必須にする。

| 観点 | 最低限確認すること |
|---|---|
| 正常系 | 1人で全時間が成立する |
| 再計画 | 辞退→部分同意→残枠の同意で全体が成立する |
| 充足判定 | 重複区間の時間を足しただけでは完了にしない |
| 候補枯渇・無応答 | 無限に待たず、必要な情報付きで終了する |
| 曖昧さ・失効 | 曖昧な返信、期限切れ、撤回を勝手に同意と扱わない |
| 手動停止 | 停止後に返信が来ても確定しない |
| 競合・重複 | 版変更、同じ返信の再送、確定の再試行で誤更新しない |
| 更新後障害 | 更新済みの通知失敗と、更新成否不明を区別する |
| 上限 | 予算・期限・回数で新規処理を止める |
| 権限・指示注入 | 他人としての同意、不正な返信命令を実行しない |

詳細な人数別分担と工数は本書に追加せず、[RFC-005](../rfc/RFC-005-delivery.md)を参照すればよい。20ケース・72試行を計画案として扱い、実施済みにしていない点は正しい。

## P2-04：「大幅な変更・追加人件費」をMVP必須にすると対象が広がる

対象：第8節186〜188行、第9節の給与・人件費計算除外、第11節250行。

「追加人件費が上限を超えるなら引き継ぐ」を実際に判定するには、追加費用の算定条件が要る。「大幅な延長・短縮」も基準となる既存勤務との関係を増やす。暫定の閾値だけを置いても、その入力・計算が必要になる。

第8節末尾の「登録された時間帯・役割だけで調整する」を主方針にして、MVPでは次に固定するのがよい。

> 既存の別勤務の変更、役割変更、人件費条件の再交渉は行わない。今回の不足枠について、事前に設定された勤務条件と本人同意の範囲だけを調整する。金額による実行可否の判定は次段階の設計で扱う。

ただし代替者の勤務にも人件費は発生するので、「費用が発生しない」という意味にはしない。実運用時の委任条件として費用上限が必要かは別途検証する。人件費判定を本当にMVPへ入れるなら、料金入力・算式・不明時の扱いを明記して工数を再見積りする。

## 代表シナリオの修正文案

> 店長が18〜22時のホール担当1人の欠勤を登録し、調整を開始する。Aは辞退する。Bが「19〜22時なら可能」と返信したため、エージェントは店舗・日付・職種・19〜22時という条件を確認し、全体が成立すれば勤務を確定してよいという本人同意を得る。残る18〜19時についてCにも同じように同意を得る。アプリは最新の勤務条件・権限・同意・重複・期限を再検査し、BとCの割当をまとめて確定する。更新後に読み戻し、店長とB・Cのテスト受信箱へ確定結果を通知する。全体が成立しない場合は部分確定せず、未充足時間と終了理由を店長へ返す。

## 推奨する修正順

1. 必須サービスの実利用、同意の成立、全体確定、通知、停止を追記する。
2. 「本書の対象外」と「MVPで実装しない」を分ける。
3. 技術上の達成条件を代理指標として定義する。
4. 数値上限と必須試験を固定し、詳細設計はRFCにリンクする。
5. 大幅な勤務変更・金額判定を将来検討へ移すか、採用するなら工数を見直す。

添付原文と既存RFC・ADRは変更していない。このレビューの修正文案も、まだチームの決定としては記録していない。

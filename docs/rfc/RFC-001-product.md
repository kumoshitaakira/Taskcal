## 1. 提案

飲食店の店長に代わり、既存スタッフへの勤務可否の打診、条件付き返信の理解、再調整、シフトへの反映を進める。仮称は「欠勤リカバリー」。名称・商標は未調査。

ユーザーは案05の採用を決定した。2人チーム、4日間、現場の専門家・協力先なし。1人はフロントエンドに強いフルスタック経験者、もう1人はAPI・DB等の経験があるが初学者に近い。旧比較資料の案02への切替案は終了し、遅延時は案05の中で範囲を縮小する。

価値の単位は「メッセージを作ること」ではなく、必要な時間枠が埋まったか、埋まらなかった理由が店長に返ったか。AIは人員を創出できない。候補に余力がない状況を、再試行で解決できるかのように扱わない。

## 2. 利用者と権限

| 役割 | 目的 | 操作 |
|---|---|---|
| 店長 | 営業準備を中断せず欠勤を埋める | 欠勤登録、調整開始、停止、引き継ぎ受領、勤務条件設定 |
| スタッフ | 自分が可能な範囲だけ回答する | 自分への打診を見る、辞退、時間提案、確定対象条件への承諾、撤回申告 |
| 運営者 | 接続・障害を管理する | デモ初期化、計測、障害診断。スタッフへのなりすましは本番で禁止 |
| エージェント | 店長から委任された範囲で調整する | 許可された候補への打診・確認、条件内の更新、停止 |

他スタッフの辞退理由、連絡先、全員分の勤務履歴はスタッフ画面へ出さない。拒否に説明を要求しない。今回、欠勤理由の入力欄自体を設けない。

## 3. MVPの境界

| 項目 | 4日間に含める | ハッカソン後 |
|---|---|---|
| 運用単位 | 架空1店舗、最大8スタッフ、1職種、同時に動く案件1件 | 複数店舗、職種、案件の競合調整 |
| 期間 | 店舗の同一営業日、最長4時間、15分単位の不足枠、必要人数1人 | 日跨ぎ、休憩を含む長時間、人数2人以上 |
| チャネル | 同一アプリ内のテスト受信箱。外部サービスは模擬 | 同意を得たLINE公式アカウント連携 |
| AI | 実際にOrcaRouterを経由する自然文抽出・限定された次の行動の選択 | 多言語、追加モデル比較 |
| 状態更新 | PostgreSQL上のシフト・履歴・結果の永続化 | 外部シフトシステムとの双方向同期 |
| UI | 店長画面、スタッフ役画面、実演ログ、初期化 | 課金、管理本部、複雑な登録画面 |
| 検証 | 主要ループ、禁止操作、競合、費用・品質比較 | 実店舗での効果測定・法務労務確認 |

天候、需要予測、食材発注、給与・勤怠計算、求人・派遣・外部採用、実従業員への自動連絡を含めない。設定上限を超える入力はエラーまたは引き継ぎにし、黙って切り捨てない。

## 4. 機能要件

| ID | 要件 | 完了の証拠 |
|---|---|---|
| FR-01 | 既存シフトから欠勤時間を選択して案件化 | 元シフトを参照し不足枠と職種を再現できる |
| FR-02 | 事前許可・勤務可能時間・スキルで候補を絞る | 除外理由を機械的なコードで示す |
| FR-03 | 1人ずつ順番に打診する | 同じ候補への同一案件の初回打診は1回のみ |
| FR-04 | 自然文から辞退・承諾意思・部分可能・曖昧さを抽出 | 原文の該当部分と抽出結果が対応する |
| FR-05 | 具体的な日時・職種を提示し本人が承諾する | 改変不能な提案内容のハッシュと認証された回答を保持 |
| FR-06 | 部分承諾を組み合わせて全時間を埋める | Bの19〜22時とCの18〜19時を別の割当として確定 |
| FR-07 | 全体が揃ったとき、一つのDB取引で反映する | 部分的な確定が残らない |
| FR-08 | 更新後の読戻しと通知を行う | 割当ID、更新前後の版、通知状態を確認できる |
| FR-09 | 枯渇・期限・矛盾・予算で止める | 終了理由と残り不足時間を出す |
| FR-10 | 重複・遅延・競合から保護する | ケース別テストで二重更新・古い承諾の適用を拒否 |
| FR-11 | 店長が介入・停止できる | 停止後の新規打診と自動確定が発生しない |
| FR-12 | モデル、費用、検査、状態を表示する | 実測値・推定値・未取得を区別する |
| FR-13 | 初期化して同じケースを再現する | デモデータのみを初期化。環境フラグで本番では無効 |

## 5. 主な利用フロー

1. 店長が欠勤登録画面で対象シフトと不足18〜22時を確認する。「この条件内で調整する」を押す。この開始が当該案件の実行委任になる。
2. アプリが入力・勤務条件・連絡許可を検査し、対象候補を算出する。情報が足りなければ開始しない。
3. Aへ具体的な日時と職種を提示して打診する。Aの辞退を記録し、理由を尋ねず次へ進む。
4. Bが「19時からなら入れます」と返信。AIが19〜22時という提案を抽出する。提示していない終業時刻は文脈からの候補として示し、確定前にBへ明示する。
5. Bに「9月20日19:00〜22:00、店舗S、ホール。この条件で調整し、全体が揃えば確定してよいですか」を示す。Bの構造化された「同意する」で当該条件への承諾を記録する。
6. Cへ18〜19時を打診し、同様に日時・職種への承諾を得る。Bの19〜22時を18〜22時に伸ばしたり、短縮したりしない。
7. 全体が揃い、同意が有効期限内で最新シフト・ルールに矛盾しなければ、一つのDB取引でB・Cを確定する。
8. 読戻しで結果を確認し、本人と店長への通知を送信する。店長の追加承認は不要。通知に失敗した場合は「割当確定・通知未完了」として見せ、完了とは区別する。
9. 全体が揃わなければ未確定の提案を期限切れにし、「18〜19時が不足。A辞退、Bは後半のみ可、C無応答」等を店長に返す。

スタッフの回答・承諾は業務上必要な相手の応答であり、店長の介入とは別に計測する。「人が一切操作しない」とは説明しない。

## 6. 画面仕様

### 店長画面

初期データの店舗、必要職種、欠勤時間、既存シフトを表示。進行中は必要枠・承諾取得済みの候補・未充足枠・締切・次の状態を表示する。「候補として承諾済み」と「シフト確定」は明確に別表示。停止ボタンには止まる範囲を記載する。確定後に停止した場合はシフトを取り消さず、修正対応の画面へ進む。

### スタッフ役画面

デモのための役切替を「架空スタッフ」と明示する。依頼された日時、職種、回答期限、確定前の状態を示す。「不可」「可能時間を提案」「提示条件に同意」の操作を分ける。同意画面では日付・時刻を省略しない。閉じるだけで同意した扱いにしない。

### 検証表示

業務タイムラインを主にし、折りたたみ領域に実使用モデル、アプリ／Routerの選択主体、計測時刻、トークン、費用、検査結果を示す。秘密情報・内部思考・不要な原文は出さない。

### 空・エラー状態

候補0件、設定未完了、AI接続失敗、予算不足、DB停止、期限切れ、二重操作、通知結果不明を別のメッセージにする。画面更新だけで業務を再実行しない。キーボードで操作でき、色だけで状態を示さない。

## 7. 成功指標と非機能要件

- 主指標：正しい割当・読戻し・模擬通知受付まで、人の追加指示なしに完了した案件の割合。
- 補助指標：正しい引き継ぎ、未充足分数、店長介入数、1完了あたり総費用、処理時間、スタッフへの通知数。
- 必須品質：禁止操作0件、二重確定0件、未承諾確定0件。これは指定テスト内の合格条件であり本番保証ではない。
- 性能目標：モデルを含まないUI読み取りp95 500ms以内、イベント受領p95 1秒以内、入力後の状態表示2秒以内。モデル処理は上限20秒／呼び出し。いずれも測定前の目標。
- 復旧：プロセス再起動後に未完了状態・期限・送信待ちを再開できる。インメモリ状態に依存しない。

## 8. リリース段階

H0は架空データと模擬チャネルで技術を確認。P1では実店舗の情報を用い、まず提案のみを既存の店長対応と比較。P2では店舗のルール・本人の同意・連携仕様を確認したうえで、承認付きで限定運用。P3で事前委任の範囲を限定して自動確定へ進む。4日間の完成をP3相当と扱わない。

具体的な得意言語、各日の稼働時間、API接続情報、総予算、公式配点、発表時間は未確認。人数・経験構成は確認済みとして計画に反映した。価格・需要・労務設定は[RFC-006](RFC-006-business.md)、運用条件は[RFC-007](RFC-007-security-operations.md)で扱う。

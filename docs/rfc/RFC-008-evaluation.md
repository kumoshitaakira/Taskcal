# RFC-008：評価計画・受入基準・実演手順

> 2026-09-20適用注記：本書は旧方式の評価仕様です。比較方法と指標は継続し、順次打診・全件構造化同意・DB単独更新の期待値は[RFC-012](RFC-012-delivery-and-acceptance.md)に合わせて改訂します。旧20ケースを現行実装の合格済みテストとは扱いません。

日付：2026-09-19／状態：評価仕様、実行結果なし  
関連：[品質ADR](../adr/ADR-011-evaluation.md)、[不変条件](RFC-002-domain.md)、[開発計画](RFC-005-delivery.md)

## 1. 何を証明するか

証明するのは、定義した条件下で返信に応じて調整が進み、本人の条件と実行上限を守って、正しい確定または引き継ぎへ至ること。実店舗の効果、法令適合、任意の日本語の理解、人手不足そのものの解決はH0の評価対象外。

APIモックを使う決定的な業務テストと、実際にOrcaRouterへ接続するモデル評価を分離する。モックだけでOrcaRouter利用を証明しない。合格基準は事前に固定する。

## 2. テストデータ

共通fixtureは2026-09-20、店舗S、ホール、欠勤18〜22時、最大8人、15分単位。スタッフの在籍・スキル・可能時間・既存勤務・連絡許可・デモ勤務ルールを記述する。案件期限と返信時刻をClockで制御する。

開発用はD01全時間可能、D02単純辞退、D03開始時刻変更、D04曖昧表現、D05期限切れ、D06勤務競合の6件。評価用の文言と組合せは分離し、Day 2終了時に固定する。調整に使った評価データを未見のテストと称さない。

スタッフsimulatorは依頼された時間とscenarioから返信する。エージェントの次行動や確定結果を録画どおりに固定しない。構造化承諾は別イベントとして発生させる。

## 4. 追加の境界試験

| ID | ケース | 必須結果 |
|---|---|---|
| B01 | 古い条件hashで同意、日時変更後の再送 | 拒否。新しい条件への同意を要求 |
| B02 | 確定前の撤回と確定後の撤回申告 | 前者は計画無効、後者は履歴を消さずATTENTION・人の変更経路 |

| B04 | 2つの確定処理・ルール変更を並行実行 | 最多1つだけ成立し、最新条件を破らない |

| B09 | 辞退履歴だけを変えて候補順位を再計算 | 順位が変わらない。欠勤者本人・連絡拒否者を候補にしない |

単体テストは区間・同意・状態の計算、実DB統合テストは排他・再起動・一意性、E2EはE01/E03/E12を主にする。すべての文言やUI配色まで試験で固定する必要はない。

## 5. モデル・ルーティング比較

同じ20ケースを、F＝全高性能、L＝全軽量、R＝タスク別切替で比較する。モデル不要のケースは呼出し0でもよい。比較するのはモデルを含む同一業務フロー全体である。

最小は20×3＝60実行。時間と事前設定予算が許せば、E03/E07/E13/E14の4件を各構成でさらに1回ずつ実行し、計72実行とする。この反復は非決定性を見る補助であり、統計的な優位性を保証しない。API課金が許可され予算が設定されるまで実評価を開始しない。

初期状態を毎回resetし、モデルID・温度・最大出力・プロンプト・Router設定を記録する。ルート以外の候補順位・業務制約は共通にする。順番による影響を減らすためF/L/Rの順をケースごとに循環させる。失敗試行を費用から除外しない。

## 6. 指標の定義

| 指標 | 算式・注意 |
|---|---|
| 正しい終了率 | 期待した割当／引き継ぎ／拒否／注意状態を満たした件数÷全評価件数 |
| 自律完了率・全件 | 店長の追加操作なしでCOMPLETEDとなった正しい件数÷全業務案件。拒否APIだけのE19/E20は業務案件の分母外 |
| 自律完了率・解決可能案件 | 同上÷fixture上、期限内に有効な候補が揃うと事前定義した案件数。後から成功しやすいものだけ選ばない |
| 禁止操作 | 未承諾・期限後・越境・重複・ルール違反の実行件数。発生箇所も保持 |
| 1完了あたり費用 | 全業務案件の推論費合計÷正しく完了した件数。完了0なら算出不可 |
| 1案件あたり費用 | 成否を含む費用合計÷実行案件数。全費用既知のものと不明ありを分ける |
| 店長介入 | 開始操作を除いた追加の判断・修正操作。スタッフ本人の承諾は別カウント |
| 処理時間 | システム能動時間と人の待ち時間を分離。デモClockの時間を実性能としない |
| スタッフ負担 | 1案件の依頼・確認・結果通知数、重複数、辞退後の追加依頼数 |
| 未充足分数 | 終了時の必要区間から確定割当で覆われた区間を引いた長さ |

「正しい引き継ぎ」は正しい終了に含めるが、自律完了に含めない。費用がUNKNOWNの実行を0円にせず、推定・予約残高とともに別表示する。

## 7. 合格基準

H0の必須条件は、E01〜E06の期待業務動作、E09〜E20とB01〜B12の禁止操作・上限・復旧条件が固定版で全て通ること。E07/E08も本人同意と充足検査の必須条件を満たすこと。自然文の正確な解釈が不確実なら確認へ止まれることを先に守る。

R構成の正しい終了率の目標は20件中18件以上。ただし18/20でも安全性必須条件に1つ違反すれば不合格。E01〜E06の主要ケースで目的を達成できない場合もデモ完成とはしない。原文解釈の不足による不要な確認などを、残りの品質改善課題として記録する。

コスト削減率の事前ノルマは設定しない。RがFに比べて品質を落とすなら、Fを残すか切替規則を直す。費用差が不明・小さい場合は、そのまま報告する。

## 8. 実演台本：3分を仮置き

| 時間 | 操作・見せる事実 |
|---|---|
| 0:00〜0:20 | 欠勤18〜22時を登録。既存スタッフ内での調整という範囲を説明 |
| 0:20〜1:10 | A辞退、B「19時から」への条件確認、C18〜19時への依頼を表示 |
| 1:10〜1:40 | 当人の同意後、2つの割当が一括確定。読戻しと通知受付を表示 |
| 1:40〜2:15 | 別fixtureで遅延・重複・矛盾の1例を投入し、勝手に確定しないことを示す |
| 2:15〜2:45 | 実使用モデル、call、実測または推定費用、F/L/R結果を表示 |
| 2:45〜3:00 | 模擬チャネル・架空データであること、次は実店舗で作業時間を検証すると説明 |

モデル処理が20秒かかる場合に備え、表示中に説明する。発表時間が異なる場合は台本を短縮する。録画・事前結果を用いた部分は再生と明示する。成功例だけで安全性を主張せず、停止する例も含める。

## 9. 審査基準との対応

| 基準 | 見せる証拠 | 限界 |
|---|---|---|
| セキュリティ | 本人同意、所属検査、キー非公開、E13/E19/E20 | 本番監査や法的適合の認証ではない |
| コストパフォーマンス | 同一fixtureのF/L/R、失敗込み費用、上限 | 実店舗の全運用費は別検証 |
| 信頼性・堅牢性 | 原子的確定、再起動、重複、競合、通知失敗 | 外部LINE／シフト連携の実保証ではない |
| 自律性 | 辞退・部分可否に応じた次行動、店長追加介入なし | 当人の回答・同意は必要 |
| アイデア・独創性 | 部分時間を組み合わせ、説明可能に完了／引き継ぎ | 市場初・競合不在は未証明 |

## 10. 残す評価成果物

`results.csv`にcase_id、構成、各版、期待結果、実結果、禁止操作、call、token、cost_kind、cost、latency、介入数を保存。`failures.md`に失敗理由と対応、`demo-recording`に固定版の実演、`runbook.md`に初期化・起動・復旧手順を残す。これらは今後の実装成果物で、このRFCに実測結果があるわけではない。

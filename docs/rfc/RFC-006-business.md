# RFC-006：ビジネスモデル・採算仮説・顧客検証

> 2026-09-20適用注記：本書は事業仮説として継続します。CSV手動取込みの負担、同時打診による通知費・スタッフ負担の追加影響は[RFC-012](RFC-012-delivery-and-acceptance.md)第7節に記録しました。料金・需要は再承認や検証済みになったわけではありません。

日付：2026-09-19／状態：事業仮説・検証前  
関連：[料金ADR](../adr/ADR-009-business.md)、[運用段階](RFC-007-security-operations.md)、[出典](../sources.md)

## 1. 誰の何を解決するか

購入者は飲食店のオーナーまたはエリア責任者、日常利用者は店長、依頼の受け手は既存スタッフ。突発欠勤のたびに候補者へ連絡し、部分的な可否を整理し、勤務を反映する中断時間を減らす。

初期顧客の仮説は1〜10店舗を運営し、各店15〜40人程度の既存スタッフがいて、月6件以上の突発調整がある事業者。ただし頻度・人数・支払意思は未調査。ROIがより明確になる月12件程度の調整がある店舗から探す。慢性的に勤務可能な人がいない店舗はAI調整の効果が出にくい。

「既存スタッフの可能時間はあるが、連絡・条件整理・反映が店長へ集中する」状態に対象を絞る。採用不足、低賃金、慢性的人員不足をソフトウェアで解決できるとは訴求しない。

## 2. 価値提案と競争

価値提案は「欠勤を登録すると、許可されたスタッフへの打診と再調整が進み、条件が揃えば反映され、揃わなければ残り不足だけが返る」。成果は店長の能動作業時間、未充足時間、誤確定、通知負担で測る。

| 代替手段 | 利点 | 本案で検証する追加価値 |
|---|---|---|
| 店長による電話・個別チャット | 導入不要、事情を理解して柔軟に対応 | 同じ調整を繰り返す時間と反映漏れを減らす |
| グループチャット | 一度に募集できる | 条件付き返信と不足区間を整理し、連絡の集中を避ける |
| 既存シフト管理 | 既に勤務情報があり利用者が慣れている | 突発案件の最後まで進む調整機能に追加対価があるか |
| 求人・スポットワーク | 店内に候補がいなくても別の人を探せる | 本案は既存スタッフ内に限定。代替採用の市場へは入らない |

Airシフトは公開価格が連携スタッフ1人あたり月330円（税込、少人数には別の下限規則）。20人なら月6,600円（税込）という比較基準になる。これは機能範囲・対象課金数が異なる価格例であり、本案の方が安い／優れるという証拠ではない。既存製品に同様の自動調整がないとも断定しない。[S09](../sources.md)

新規性の主張は「チャットにAIを入れた」では弱い。本人の時間条件を守る部分枠組合せ、途中変更への再計画、上限と証拠を備えた業務完了を実演する。事業上の差別化は、接続先・導入負担・現場での完了率を検証してから判断する。

## 3. ビジネスモデルの全体像

| 項目 | 初期仮説 |
|---|---|
| 顧客セグメント | 上記の突発調整頻度が高い飲食事業者 |
| 課金単位 | 1店舗／月。席数や従業員個人に成功報酬を課さない |
| 提供価値 | 調整の代行、条件確認、反映・引き継ぎ、説明可能な履歴 |
| 販売経路 | 店舗への直接ヒアリング、紹介、地域の事業者ネットワーク。まだ契約先なし |
| 顧客との関係 | 初回のルール・連絡先・権限確認と、初期運用の伴走 |
| 主要活動 | 同意・勤務ルールの管理、連携の保守、例外対応、品質評価 |
| 主要資源 | 業務状態機械、検証ケース、連携adapter、現場から同意を得た運用知識 |
| 協力先候補 | 店舗責任者、シフト管理提供者、労務・個人情報の専門家。未確保 |
| コスト | 推論、DB・ホスト、メッセージ、決済、導入、サポート、連携保守 |
| 将来の拡張 | 同一事業者の複数店舗調整。ただし雇用・移動条件等を確認後 |

## 4. 料金の検証案

最初の価格仮説は月2,980円／店舗（税別）、月10案件まで。年額割引は最初から設けず、解約可能な月払いで支払意思を測る。月4,980円の上位案は頻度が高く追加価値を確認できた顧客だけで別途検証し、確定したプランとして宣伝しない。

「1案件」は不足枠に対して調整を開始した単位。同じ欠勤の再試行・再開は同一案件で二重課金しない。完了／引き継ぎを区別して利用実績を示す。利用者の開始前取消とシステム障害起因の終了は月間件数へ算入しない案とし、契約前に定義する。成功件数だけに課金すると、無理に確定させる動機や成果帰属の争いが生まれやすい。

上限超過時は翌月待ち・明示的な追加購入・プラン変更を提示し、勝手に従量課金しない。金額、返金、障害時の取扱い、最低利用期間は実店舗契約前に確定。ハッカソンで決済機能を作らない。

## 5. LINE費用を無視しない設計

日本向けLINE公式アカウントの公開料金は、無料プランが月200通、ライトが月5,000円・5,000通、スタンダードが月15,000円・30,000通（有料プランは税別）。無料・ライトには追加メッセージ枠がなく、スタンダードの追加は数量に応じた単価。Push等はカウント対象で、Reply APIなどは扱いが異なる。[S05](../sources.md)

したがって「連絡1回＝一律3円」と置かない。打診・再確認・確定通知の送信方式ごとに件数を集計する。無料枠は店舗の既存配信とも共有されるため、残枠を全て使えるとは限らない。新規専用アカウントに有料プランが必要なら、本サービスよりチャネル料金の方が大きくなる。

初期事業仮説は顧客保有の公式アカウントを接続し、LINE料金を顧客が直接負担する方式。既存アカウントのwebhook・他サービスとの競合、接続許可、スタッフとの紐づけ、残枠取得可否は導入前に確認する。接続できない顧客へ導入を約束しない。複数顧客を1つのアカウントへ混在させて安く見せる設計にはしない。

## 6. ユニットエコノミクス：すべて仮定の試算

税別月額2,980円、決済手数料3.6%（仮定、決済会社未選定）、ホスト配賦150円、10案件×推論10円＝100円、サポート労務3,000円／時間を仮置きする。実測された推論費ではない。LINEは顧客直接払いのため提供側0円として分離する。ホスト配賦150円も規模で変わり、固定費との二重計上を避ける。

| 月間シナリオ | サポート費 | 提供側変動・配賦費合計 | 限界利益相当 | 売上比 |
|---|---:|---:|---:|---:|
| 軽い：5分 | 250円 | 607.28円 | 2,372.72円 | 79.6% |
| 基準：15分 | 750円 | 1,107.28円 | 1,872.72円 | 62.8% |
| 重い：60分 | 3,000円 | 3,357.28円 | −377.28円 | −12.7% |
| 基準＋提供側が専用LINEライトを負担 | 750円 | 6,107.28円 | −3,127.28円 | −104.9% |

式は`2,980 − (2,980×0.036 + 150 + 100 + サポート費 + 提供側のLINE費)`。営業費・開発費・税・返金・貸倒・固定運営費を引く前であり、営業利益率ではない。

推論が1案件50円なら基準利益は1,472.72円へ400円低下する。推論の節約だけでなく、問い合わせが月15分から60分へ増える影響の方が大きい。初期導入を標準化できるかが重要。

獲得費6,000円＋初期導入費3,000円という仮定なら、基準の回収期間は9,000÷1,872.72＝約4.8か月。獲得費12,000円＋導入費6,000円なら約9.6か月。解約率の実績がないのでLTVを断定しない。未回収での解約、営業工数、オンボーディング離脱を記録する。

月10店舗の売上は29,800円、50店舗149,000円、100店舗298,000円。仮に上記費用とは別に月150,000円の固定費が必要なら基準ケースの損益分岐は81店舗。これは算術上の例で、創業者の給与等を含む実際の固定費は未確定。年商から逆算した根拠のない成長予測は置かない。

## 7. 顧客側ROIと購入条件

1案件で店長の能動作業を15分削減、時間価値2,000円／時間という仮説なら、1件500円。

| 月間件数 | 時間価値 | 月額2,980円のみとの比較 |
|---:|---:|---|
| 2 | 1,000円 | 費用を下回る |
| 6 | 3,000円 | ほぼ同額。導入負担を考えると弱い |
| 12 | 6,000円 | 約2倍。ただし実際に15分削減できることが前提 |

新規LINEライト代を加えると月7,980円となり、同じ仮定では16案件でようやく相殺。既存アカウントの支出が増えない顧客と、新規固定費が発生する顧客を別に評価する。月10案件プランを超える16件の実運用料金は未定のため、これも最低限の費用だけでの試算である。

上表の12件も10件枠を超えるため、月2,980円のまま利用できる料金案ではなく、価格感度をみる計算である。実料金が4,980円なら12件の6,000円価値との差は1,020円に縮む。月10件上限・価格・提供価値が整合するかを検証し、相性が悪ければ上限または対象顧客を見直す。

時間の削減は直ちに人件費削減と同じではない。売上回復・欠勤解消率・離職改善は別途測定できたときのみ主張する。作業時間を減らしてもスタッフ通知負担が増えすぎるなら不採用。

## 8. 検証計画と中止条件

| 段階 | 方法 | 合格仮説・判断 | 記録 |
|---|---|---|---|
| 発見 | 店長・責任者8人、スタッフ8人への個別ヒアリングを目標 | 直近の実例、頻度、能動時間、代替手段、追加支払意思を確認 | 匿名化した案件の事実。人数は募集目標で実績ではない |
| 課題確認 | 提供許可を得た過去案件を再構成 | 調整余地のある欠勤と、人手自体がない欠勤を区別 | 候補数、部分可否、未充足理由 |
| P1 | 3店舗を目標、2週間の通常運用記録＋1週間の影運用 | AI案が実際の条件を守る。無断送信なし | 期待結果・不一致・導入時間 |
| P2 | 本人同意と店長承認を備えた2週間の限定運用 | 能動時間中央値40%削減、重大な無同意・重複確定0 | 実案件30件未満なら効果判断を延期 |
| 支払検証 | 最終1週間で実料金の継続提案 | 3店舗中2店舗が実際に有料継続することを目標 | 口頭の好意と支払を区別 |
| 継続 | 8週間以上観察 | 利用頻度、サポート、解約、スタッフ苦情を評価 | 対象が少なければ一般化しない |

この検証には協力先の募集が必要で、4日間で顧客検証を終える前提を置かない。ヒアリング相手への連絡・営業は本資料作成では実施していない。

質問は「使いたいですか」より「直近の欠勤で誰に何回連絡し、何分かかり、どこが埋まらなかったか」「既存ツールで困っている点」「誰が予算を決めるか」を優先。スタッフには断りやすさ・連絡時刻・同意画面・勤務確定の認識を確認する。

中止または変更条件は、頻度が少なくROIが出ない、接続導入に恒常的な個別開発が必要、候補の余力がない、同意取得が圧迫的、無料代替で十分、サポート原価が継続的に売価を上回る場合。価格を下げる前に対象顧客・提供範囲を見直す。

## 9. 契約・責任・運用の境界

顧客が勤務ルールと委任範囲を設定し、サービスはその範囲の調整を支援する。自動化の範囲、連絡先の利用目的、データ処理先、結果通知、変更・撤回、障害時の人への引き継ぎ、解約・データ書出しを契約に明記する。AIの免責文だけで勤務管理責任や製品品質を置き換えない。

既存雇用者内の調整に限定するが、それだけで特定の法規制が適用されないと断定しない。実利用前に労務・契約・個人情報の適用関係を専門家と確認する。正式なSLAや損害補償水準は実測・契約前に決定し、MVPの目標値を保証に転記しない。

## 10. 持続的な強みの候補

推論モデルやRouter単体は模倣可能。強みになり得るのは、店舗ごとの条件を短時間で安全に設定する導入手順、同意を損なわない例外処理、連携の確実性、測定済みの完了品質である。従業員の私生活や返信内容の大量蓄積を競争優位として狙わない。

# RFC-004：エージェントの制御とOrcaRouterの利用

> 2026-09-20適用注記：OrcaRouter利用・費用予約・計測の考え方は継続します。全件ボタン同意と順次打診を前提にした処理は[RFC-011](RFC-011-outreach-and-state.md)へ改訂。10call等は同時打診の件数に対して再検証する暫定値です。

日付：2026-09-19／状態：実装ベースライン案  
関連：[AIの責任ADR](../adr/ADR-004-agent-boundary.md)、[情報・費用ADR](../adr/ADR-007-router-budget.md)

## 1. 自律性の範囲

単一エージェントが、返信と業務状態を観測し、許可された次の行動を選ぶ。最終的な勤務計算、候補順位、同意判定、更新は決定的なコードが担う。LLMが複雑な勤務最適化問題を解くことを必須にしない。

仕事は`observe → interpret → choose → validate → execute → observe`。WAITINGではプロセスを回し続けず、返信または期限イベントまで終了する。モデルの出力は提案であり、ツール実行権限ではない。

## 2. 1ステップのアルゴリズム

1. case、直近イベント、許可範囲、未充足区間、候補の匿名ID、計測状態をロードする。
2. 終端状態・期限・予算・回数・停止をモデル呼び出し前に検査する。
3. 構造化ボタンの返信はコードで処理。自然文があれば軽量モデルで抽出する。
4. JSON schema、原文の根拠範囲、時刻、指示された条件との一致を検査する。
5. 構造不正なら修復または高性能モデルへの昇格を最大1回。意味が曖昧なら強いモデルで断定せず、スタッフに確認する。
6. 状態に対して合法な行動だけを列挙する。例：条件確認、次候補へ打診、全体計画作成、人への引き継ぎ。
7. AIが行動と根拠コードを選ぶ。決定的な遷移で十分な箇所はモデルを呼ばない。
8. アプリが現在のcase_versionと合法行動を再検査し、実行ID付きのサービス関数を呼ぶ。
9. 結果を保存し、次イベントが必要ならジョブを登録する。失敗を成功扱いにせず、観測して再計画する。

## 3. 返信解釈の出力契約

```json
{
  "intent":"PARTIAL_AVAILABILITY",
  "offerId":"offer-opaque-id",
  "proposedLocalStart":"2026-09-20T19:00:00+09:00",
  "proposedLocalEnd":"2026-09-20T22:00:00+09:00",
  "evidence":[{"start":0,"end":3,"text":"19時"}],
  "needsClarification":true,
  "clarificationCode":"CONFIRM_EXACT_TERMS"
}
```

intentは`DECLINE / AVAILABILITY / PARTIAL_AVAILABILITY / AMBIGUOUS / WITHDRAWAL_REQUEST / OTHER`の列挙。`CONSENT`や`COMMIT`は出力させない。ISO日時をモデルが出しても、元のOfferの日付・時間範囲と照合する。evidenceのoffsetと文字列一致をコードで検査する。根拠があっても解釈が正しい保証にはならないため、確定対象の具体的条件を本人へ再提示する。

「19時からなら」「前半だけ」「たぶん」「休憩が取れれば」などは条件付き意思。断定的な可否へ変換しない。病名や家庭事情は抽出対象にしない。入力が長すぎる場合は途中切断して推定せず、短い回答を求める。

## 4. 行動選択の契約

```json
{
  "action":"REQUEST_TERMS_CONFIRMATION",
  "targetId":"proposal-opaque-id",
  "reasonCode":"PARTIAL_INTERVAL_DETECTED",
  "evidenceIds":["reply-opaque-id"],
  "expectedCaseVersion":4
}
```

行動は`SEND_NEXT_OFFER / REQUEST_TERMS_CONFIRMATION / BUILD_COVERAGE_PLAN / HANDOFF`。`WAIT`はアプリの状態に応じて処理し、繰り返しLLMに選ばせない。自由な宛先、SQL、任意URL、コード実行、ルール変更の引数は提供しない。`BUILD_COVERAGE_PLAN`後の確定はアプリが全不変条件を検査して行う。

## 5. モデルへ渡す情報

渡すのは案件内でのみ有効な匿名ID、日付・必要時間・役割、正規化した候補条件、当人の返信、選べる行動。氏名、電話番号、LINE user ID、全従業員の履歴、欠勤理由、他人の返信全文は渡さない。

自然文はモデル前に不要な連絡先等をマスクする。ただしパターン検知で完全な匿名化を保証しない。MVPでは架空データだけを使い、本番では利用目的・提供先・保持を別途決める。

外部の返信は引用されたデータとして扱う。system指示と同じ権限を与えない。APIキー・宛先・ルールはモデルから見えない場所に置き、モデル出力の命令に関係なくサーバーで検査する。

## 6. ルーティングの方針

| タスク | 初期経路 | 切替・停止 |
|---|---|---|
| 短い自然文の条件抽出 | 軽量モデル | schema不正・根拠不一致で最大1回修復／昇格 |
| 複合条件の解釈 | 高性能モデルまたはRouterの確認済み規則 | それでも曖昧なら本人へ確認 |
| 次行動の選択 | 合法行動だけを渡す軽量モデル | 検査違反で1回修復、その後引き継ぎ |
| 時間・同意・確定・通知 | コード | モデルを呼ばない |

通常時のLLM callは案件内10回以内。修復・再試行・昇格も含む。HTTPタイムアウト20秒、同じネットワーク呼び出しの再試行最大1回、全案件通算上限も確認する。LLM自己申告のconfidenceだけで安全な確定や安い経路を選ばない。

OrcaRouterのDSL・複数モデル機能は公開仕様で確認済みだが、当日のアカウント権限と実使用モデルの取得は未確認。まず名前付きルーターで2種類のワークロードを比較する。規則を設定できなければアプリ側でモデルIDを選び、どちらもOrcaRouter経由で呼ぶ。その場合はrouting_source=APPLICATIONと表示し、ゲートウェイ側自動振り分けと称さない。[S01](../sources.md)

候補モデル名と単価はDay 1の利用可能一覧で決める。ベンダーの一般的な節約率は採用しない。SDKの暗黙retry、ゲートウェイの未確認のfallback・複数呼び出しが料金にどう影響するかも確かめる。

## 7. 費用上限

予算は独立した設定として`case_call_limit`、`case_spend_limit`、`run_spend_limit`を持つ。金額はUSDの整数micro単位で記録し、円換算は表示時に換算日時とレートを添える。未設定なら有料呼び出しを開始しない。資料作成は課金承認ではない。

呼び出し前に、入力長・出力上限・候補モデル単価から保守的な費用を予約する。並行呼び出しは予約残額込みで検査する。実際のusage・費用を取得したら精算し、失敗・タイムアウトでも0円と扱わない。課金不明はUNKNOWN_CHARGEとして予約を残す。

ゲートウェイ内部の呼び出し数・課金上限を確認できない構成では、アプリの予約だけで厳密な金額上限を保証しない。その経路を無効にするか、提供元の利用上限とアプリの回数・トークン制限を併用し、上限の限界を表示する。接続テストで結果不明なら有料の再試行を連発しない。

## 8. 可観測性

`case_id, run_id, step, request_id, prompt_version, rules_version, requested_model, resolved_model, routing_source, latency_ms, usage, cost, cost_kind, validation_result, action_key`を記録する。モデルが返したモデル名をそのまま実使用モデルの証拠にしない。API応答・正式ログから取れない項目はUNKNOWNとする。

モデルの内部思考を取得・保存する必要はない。選択した行動、参照条件、検査結果、状態の前後があれば説明できる。失敗時のHTTPログに認証ヘッダーや本文を丸ごと出力しない。

## 9. プロンプトと評価の変更管理

プロンプト、schema、モデルID、Router設定、温度、最大出力、入力例を版管理する。開発用6ケースで調整し、評価用20ケースは固定する。最終評価を見て修正した場合は修正後の再評価と明記し、初回結果を隠さない。モデルを変えても同意・勤務条件の検査は同一である。

## 10. 完了判定

Day 1は実モデルのJSON受信と実使用モデル・費用の記録。Day 2は辞退・部分承諾によって次行動が変わること。Day 3は全高性能／全軽量／切替の比較。品質差がなければ複雑なRouter規則を増やさず、実測に基づく最小の構成を残す。

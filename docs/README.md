# Taskcal 設計記録

更新：2026-09-20／現在の設計資料：データモデルv0.4＋レビュー反映案  
収録：**RFC 12本・ADR 20本**、未決事項、変更履歴、提供資料とレビュー。アプリの実装・実測は未実施。

サービス名はユーザー指定により **Taskcal**。旧資料の「案05」「欠勤リカバリー」は同じ企画の過去の呼称として保持します。名称の判断は[ADR-020](adr/ADR-020-taskcal-name.md)を参照してください。

## 現在の結論

2人・4日間で、架空店舗の突発欠勤に対する調整を作る。現行文書の方針は、適格者全員への個別同時打診、明確な自然文返信からの承諾、CSV勤務表の入出力、模擬メッセージ環境、OrcaRouter経由の推論。

今回の中心は「更新CSVを出力すること」と「その勤務表を正式版として採用すること」を分ける設計。正式採用する方式を推奨しているが、選択が残る項目は未決として記録している。**記録への整理を、全提案の個別承認や実装完了とは扱わない。**

RFCは要件・設計・実装と検証の契約、ADRは選択理由・代替案・帰結を残す。提供文書の方針、レビューによる提案、未決事項を分けて読めるようにした。

## 前提と未検証事項

ユーザー確認済みなのは案05・4日・2人と経験構成・協力先なし。具体的な言語、各日の稼働、実接続、予算、発表条件は未確認。顧客需要・価格・時間削減・実店舗の勤務ルールは仮説または今後の検証対象。

改訂の40人時は1人1日6時間を仮定した計画で、実績や保証ではない。現在の成果は設計記録であり、接続・CSV処理・試験・営業・実従業員への連絡を実施したものではない。

## 資料の履歴と更新方法

[元資料とレビューの索引](references/README.md)、[外部出典・確認範囲](sources.md)を参照。提供されたv0.2/v0.3/v0.4は原文のまま保存した。レビューの内部リンクだけを同梱先に合わせている。

変更時は、Q番号の選択→関連ADRの状態・理由→RFC→fixtureの期待値の順に揃える。過去のADR本文を新しい理由で上書きしない。新しい決定が置き換える範囲を明記し、相互リンクを残す。

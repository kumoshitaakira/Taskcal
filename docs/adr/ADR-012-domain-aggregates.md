# ADR-012：業務主体・値・記録を分け、Scheduleを勤務表集約とする

日付：2026-09-20／状態：v0.4に明記された現行設計方針、未実装  
詳細：[RFC-009](../rfc/RFC-009-domain-v04.md)／更新対象：旧RFC-002/003のモデル

## 背景

v0.2のクラスは、業務エンティティ、値、計算結果、ログが混在していた。勤務を通常・代替の別正本にすると、集計と重複検査が分裂する。

## 決定として記録する方針

Store、Staff、Schedule、AbsenceCaseを集約ルートとする。ShiftAssignmentはSchedule内で通常・代替を共通に管理する。役割は固定RoleCode。連絡先、可能時間、月次上限はStaffの値とする。

選定はSelectionResult、返信・解釈は不変レコード、操作はProcessingEventへ分ける。更新要求はScheduleUpdate、終了結果はCaseOutcome。CandidateEvaluationを独立した業務主体にはしない。

## 選択肢と理由

すべてにIDと個別ライフサイクルを与える案はMVPに不要な操作を増やす。逆に全てを案件の可変JSONに混ぜる案は、同意・更新結果の証拠を失いやすい。現在状態と固定された記録の役割を分ける方針を選ぶ。

## 帰結

クラス数とテーブル数は一致しなくてよい。固定RoleCodeは店舗ごとの役割管理には不足するが、今回は対象外。集約を分けても複数集約にまたがる一括確定の契約は別途必要。

## 検証・見直し

勤務の二重計上がないこと、承諾・選定・勤務の由来を追えることを確認する。複数必要枠の個別取消や店舗独自の役割管理が必要になれば再検討する。

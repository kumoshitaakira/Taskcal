# ADR-024：状態変更の入口をServer Actionにし、冪等キーをフォームへ埋める

日付：2026-09-22／状態：実装済み（Day 2・担当A）
詳細：[ADR-006](ADR-006-idempotency.md)、[RFC-009 D07](../rfc/RFC-009-domain-v04.md)、[RFC-012 §3.1](../rfc/RFC-012-delivery-and-acceptance.md)
適用範囲：`src/app/` の画面から起こす状態変更。adapter・worker・外部連携の経路は変えない。

## 背景

ADR-006 と D07 は「同じ操作IDで異なる内容を拒否し、同一内容は保存済み結果を返す」ことを求める。
この規則が効くのは、**操作IDが再試行をまたいで同じ値になる場合だけ**である。画面から
サーバーへ操作IDをどう運ぶかを決めないと、二重クリック・再読込・ブラウザの戻る操作が
毎回新しい操作IDを作り、冪等性の仕組みが素通りになる。

Next.js App Router では、状態変更の入口に Server Action と Route Handler の2つがある。
どちらを既定にするかは、後から変えると全画面と全 use case のシグネチャに波及する。

Day 1 の時点で `src/app/` にクライアントコンポーネントは1つも無く、画面はすべて
サーバーコンポーネントだった。

## 決定

**画面から起こす状態変更の入口を Server Action にする。** サーバーコンポーネントが描画時に
操作IDを作り、`<input type="hidden" name="operationId">` に埋める。二重クリック・再読込・
戻る操作は同じフォームを再送するため、すべて同じ操作IDになり、`operation_result` の照合で
`REPLAY` になる。

**外部から叩ける安定したURLが要る経路だけ Route Handler にする。** 現在の該当は模擬provider
の受信口（`/api/mock-channel/inbound`）のみ。curl・統合テスト・デモの再現から同じ経路を
通す必要があり、とくに A15（接続違いの同じ eventId）は HTTP 経路で再現できることに意味がある。
Server Action は安定した外部URLを持たないため、これには使えない。

操作の結果は、**あらかじめ決めた通知コード**を付けた redirect で返す。文言そのものをURLへ
載せない。載せると、任意の文字列を画面へ出すリンクを作れてしまう。

## 選択肢

Route Handler を既定にする案も、`<form method="post" action="/api/...">` で同じことはできる。
ただし送信後の遷移と再検証を毎回自前で書くことになり、戻り値を型付きで受け取れない。
冪等キーの扱いは Server Action と同じにできるので、ここは決め手にならない。

クライアントコンポーネントで `useActionState` を使えば、戻り値をそのまま画面へ出せる。
ただし状態変更のある画面すべてがクライアントコンポーネントになる。JSが無効なら操作できず、
デモの再現手段も減る。得られるのは表示の滑らかさだけで、4日間の範囲では釣り合わない。

操作IDをサーバー側で毎回生成する案は、冪等性が働かない。再試行が別の操作になり、
二重クリックで案件が2つできる。

## 帰結

`"use client"` を1つも増やさずに、欠勤登録・打診開始・返信投入が動く。JSが無い環境でも
フォーム送信が成立する。

結果表示は通知コードの語彙に縛られる。新しい失敗の種類を画面へ出すには、
`src/app/_components/notice.tsx` へコードを足す必要がある。細かい理由を出したい場合は、
コードを増やすか、画面側の設計を見直す。

操作IDが描画時に決まるため、**同じ画面を開いたまま別の操作をすると同じキーになる**。
案件作成は描画ごとに新しいIDを振り、打診開始は案件IDから決めている（同じ案件への打診開始は
何度実行しても一つ）。新しい操作を足すときは、どちらの決め方が正しいかを都度選ぶ。

## 検証

D07（同じ操作IDで内容が違えば拒否）、A15（宛先を含む内容ハッシュ）。
画面からの二重クリック・再読込が案件・打診を増やさないことを、`operation_result` の
`REPLAY` で確認する。

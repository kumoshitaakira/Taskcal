# ADR-006：DB取引と永続ジョブで再試行・競合を制御する

> 2026-09-20適用範囲更新：DBだけを勤務正本とする前提は[ADR-015](ADR-015-csv-source.md)へ変更。CSVの正式採用・復旧は[ADR-016](ADR-016-csv-adoption.md)の提案とQ01へ移します。実行ID・永続状態・結果照合の原則は継続。以下は当時の判断記録です。

日付：2026-09-19／状態：設計上の暫定決定  
詳細：[RFC-003](../rfc/RFC-003-implementation.md)

## 背景

HTTPタイムアウトやworker停止は「処理されなかった」ことを意味しない。モデルと送信先とDBを一つのトランザクションにできない。メモリ内ループは再起動で期限や実行結果を失う。

## 決定

case_version、schedule_revision、policy_version、同意状態を確定直前に検査する。store→case→staff/consentの順でロックし、同じ種類の行はID順に固定する。全割当・case・実行結果・outboxを同じDB取引で更新する。重複勤務はDB制約でも拒否する。

action_keyとrequest_hashで二重更新を防ぐ。Inboxで受信重複を排除し、Outboxで送信待ちを保存。workerはleaseとfence_tokenを使い、古い実行結果を破棄する。外部API待ちはDBロック外。状態の正本は現在状態テーブルで、イベントは証拠・連携用。

## 選択肢

メモリだけのループは短い実演には簡単だが障害復旧が成立しない。分散イベント基盤は規模に適するが4日間では運用が大きい。DBを軸にした小さな永続処理を採用する。

## 結果と不利益

重複実行・停止から復旧できるが、外部メッセージの到達が厳密に一度だけとは保証できない。受付不明や課金不明の状態が必要。DB以外へ勤務の正本を移す場合はこの保証を再設計する。

## 検証・見直し

E15〜E18、B04〜B06/B10/B11を実DBで試す。複数店舗・複数workerで負荷や運用が問題になれば専用キューを検討する。外部シフト連携を追加する前に正本・再照合・補償を別RFCで決める。

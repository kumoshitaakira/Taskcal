# ADR-022：引き継ぎを「自動調整の終了」と定義し、採用事実を状態と別に保持する

日付：2026-09-21／状態：ユーザー承認済み。実装はDay 2以降
詳細：[RFC-011](../rfc/RFC-011-outreach-and-state.md)、[RFC-010](../rfc/RFC-010-csv-authority.md)
更新範囲：[RFC-011](../rfc/RFC-011-outreach-and-state.md) §5の状態図と、`AbsenceCase`の状態の意味を更新する。ADR-017の「対象ごとに状態を分離する」方針は継続する。

## 背景

RFC-011 §5の状態図には、出口の無い経路が三つある。実装時に判明した。

- 照合が恒久的に不能なとき、`ReconcileRequired`の出口は`Committed`（採用済みと断定）か`Coordinating`（未採用と断定）しかない。どちらも持っていない事実の断定になる。§5本文は「ReconcileRequiredまたはAttentionとして人の対応を記録し、未確定と断定して終端へ落とさない」と書いており、本文と図が食い違う。
- 読戻し・通知が復旧しない`Attention`から終端へ行けず、案件が永久に非終端のまま残る。
- `Preparing`中に予算・回数・期限へ達した場合の経路が無い。

同時に、RFC-011 §5の表は`AbsenceCase`の状態を「調整中・確定準備・確定済み・要対応・完了・**未確定で引き継ぎ**・停止」と定義している。矢印だけを足すと、採用済みや成否不明の案件まで「未確定」と表示しかねない。

## 決定

`HandedOff`を「**自動調整を終了し、人へ対応を引き継いだ**」と定義する。「未確定」を意味しない。案件を終端にすること自体は目的ではなく、事実を保持して人へ渡せることが条件である。

採用の事実は案件状態と別に保持する。`ScheduleUpdate`の`ADOPTED`／`REJECTED`／`RECONCILE_REQUIRED`と、正式版参照を正とし、案件状態から採用可否を推定しない。画面は「未採用」「採用済み」「成否不明」を区別して表示する。成否不明の`ScheduleUpdate`を不採用へ変更しない。操作IDと照合経路を残す。

追加する遷移と、その条件は次のとおり。

| 遷移 | 許可する条件 |
|---|---|
| `ReconcileRequired → Attention` | 照合が継続不能。未採用とも採用済みとも断定しない。成否不明のまま人の対応を記録する |
| `Attention → HandedOff` | 人が対応を引き取った。採用事実は保持したまま終端へ移す。未確定と表示しない |
| `Preparing → HandedOff` | **未採用を確認できた場合に限る**。正式採用と同じ排他規則で停止を確定させる |

`Attention → Reporting`は、**採用済みと確認でき、正式版の読戻しが一致した場合だけ**許可する。読戻しが未確認のまま通知処理へ進まない。

`Preparing`中に予算・回数・期限へ達した場合、期限の検知だけで引き継がない。並行する正式採用の結果を先に確定させる。結果が不明なら`ReconcileRequired`、採用済みなら確定事実を保持して`Committed`以降の経路へ進む。

## 選択肢

矢印だけを追加する案は小さいが、`HandedOff`の既存の意味（未確定）が残るため、採用済みの案件を未確定と表示する。`Attention`を終端にしない案は、状態の意味を変えずに済むが、復旧しない案件が永久に非終端となり、A13・A18の「既確定の事実を保持して引き継ぐ」を状態で表現できない。成否不明を`Rejected`へ落として終端化する案は、確定済みかもしれない勤務を未確定へ戻すため採らない。

## 帰結

案件状態だけを見て「確定したか」を判断できなくなる。画面・指標・通知は`ScheduleUpdate`と正式版参照を参照する必要がある。終端に達した案件にも、採用済み・未採用・成否不明の区別が残る。

引き継ぎ理由（枯渇・期限・上限・照合不能・通知失敗）を保持しないと、`HandedOff`が何を意味するか説明できない。理由と、その時点の採用事実を併せて記録する。

## 検証

A03（正式採用直後の応答喪失）、A13（確定通知失敗／終了後の追加返信）、A18（停止、予算・回数・期限到達）。いずれも、終端へ落とすことではなく、事実を保持して人へ渡せることを期待値とする。

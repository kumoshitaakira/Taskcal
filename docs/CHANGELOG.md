# 設計記録の変更履歴

## 2026-09-22：Day 2（担当A）— 案件・打診・受信・承諾を実装

動くようになった範囲は、**欠勤の登録 → 適格候補への同時打診 → 模擬受信箱への送信 →
返信の受信と永続化 → 進捗画面**。返信の解釈は実装したが、OrcaRouterの接続情報と金額予算が
未取得のため**実行していない**（模擬結果は返さない）。CSV取込・候補選定・正式採用は未実装。

- `src/contracts/` へ承諾（`commitment.ts`）、選定結果と担当Bへの口（`selection.ts`）、
  永続化の口（`repository.ts`）、打診の遷移表を追加。README が「まだ契約に無いもの」として
  挙げていた3項目を埋めた。Bの確認待ち。
- migration 0002〜0009を追加。D02・D04・D05・D07・A12・A15・ADR-006・ADR-022 の各条件を
  DB制約として置いた。正式採用を実装するのは次段階だが、二重採用を止める制約はここで入れた
  （適用済みmigrationは書き換えられないため）。
- **migration番号帯を 0002-0019=A / 0020-=B に分けた。** `scripts/migrate.ts` が適用順の逆転を
  拒否するため、2人が交互に番号を取ると片方が永久に適用できなくなる。
  これは RFC-012 §3.1 の所有表（「B作成・A承認」）に対する**運用上の例外**であり、
  所有の変更ではない。ADR-021 に従いBの確認が要る。
- [ADR-024](adr/ADR-024-server-action-entry.md) を追加。状態変更の入口を Server Action にし、
  冪等キー（操作ID）をフォームへ埋める。ADR-006 / D07 を画面層まで通すための判断。
- `roster-eligibility.ts` は**適格性検査ではない**。D01の名簿部分だけを見ており、可能時間・
  月次上限・勤務の重複は未検査（担当B）。正式採用直前の再検査は `NOT_IMPLEMENTED` を投げる。
- 実際に検証した受入ケースは A11・A12・A15 と A18 の一部だけ。他は未実行。
- 設計文書（RFC）の本文は変更していない。追加したのはADR-024と各READMEのみ。

### 実装中に見つけて直した食い違い

- `schedule-update.ts` に終端状態の宣言が無く、未知の状態を他の3つの状態機械と違って
  TypeError にしていた。`TERMINAL_SCHEDULE_UPDATE_STATES` を追加し `INVALID_INPUT` に揃えた。
- `check-consistency.ts` の対称性検査が `evaluateRule` を呼ばず判定を複製していたため、
  テストが見ている判定と実際に走る判定が別物だった。
- `date` 列を `Date` で受けると、JSTでは `toISOString()` が前日になり営業日が1日ずれた。
  SQL側で `to_char` して文字列で受ける形に統一し、対称性検査へ規則を追加した。

## 記録のステータス

「ユーザー確認済み」は会話で明示された条件。「現行設計方針」は提供されたv0.4に書かれた方針。「提案」はレビューによる具体化。「未決」は複数の選択肢が残るもの。どの状態も実装・検証済みとは同義ではない。

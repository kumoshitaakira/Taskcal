# src/app

**担当A** — 店長画面、スタッフ画面、Route Handler（RFC-012 §3.1）。

## 状態変更の入口は Server Action

[ADR-023](../../docs/adr/ADR-023-server-action-entry.md)。

サーバーコンポーネントが描画時に操作IDを作り、`<input type="hidden" name="operationId">`
へ埋める。二重クリック・再読込・戻る操作は同じフォームを再送するため、すべて同じ操作IDに
なり、`operation_result` の照合で `REPLAY` になる（ADR-006 / D07）。

**操作IDの決め方を都度選ぶこと。**

| 操作 | 操作ID | 理由 |
|---|---|---|
| 欠勤の登録 | 描画ごとの新しいID | 別の欠勤は別の操作 |
| 打診の開始 | 案件IDから決める | 同じ案件への打診開始は何度でも一つ |
| 送信 | 打診IDと種別から決める | 再試行で作り直さない |
| 返信の投入 | 描画ごとの新しいイベントID | 二重送信は同じ受信イベントになる |

## `"use client"` を増やさない

現在この配下にクライアントコンポーネントは無い。JSが無くてもフォーム送信が動き、
デモの再現手段が減らない。

そのため、操作の結果は**あらかじめ決めた通知コード**を付けた redirect で返す
（`_components/notice.tsx`）。**文言そのものをURLへ載せない。** 載せると、任意の文字列を
画面へ出すリンクを作れてしまう。新しい失敗の種類を出したいときは通知コードを足す。

## Route Handler を使う条件

外部から叩ける安定したURLが要る場合だけ。現在の該当は模擬providerの受信口
（`api/mock-channel/inbound`）のみ。curl・統合テスト・デモの再現から同じ経路を通すため、
とくに A15（接続違いの同じ eventId）を HTTP 経路で再現できることに意味がある。

## 表示の規則

案件・相手別対話・勤務表更新・メッセージ配送・採用事実を**別々のタグ**で出す
（ADR-017 / ADR-022）。1つに畳むと、採用済みなのに通知が失敗した案件を「未確定」と
表示しかねない。

- 照合が必要・結果不明・引き継ぎ済みは `tag-warn`。**`tag-bad` にしない**（断定しない）。
- 未送信（`SendRefused`）は「失敗」と書かず、理由を出す。配送失敗と区別する。
- 未実装の機能は「未実装」として出す。空欄や「正常」にしない。

スタイルは `globals.css` の1ファイル。Tailwind・CSS Modules は入れない。
